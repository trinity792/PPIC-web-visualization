# Visualization Specification

> [!info] Who this document is for and how to read it
> This is an **as-built specification** - everything described here is shipped and verified. The first two sections are for anyone: what the feature is for, and how the two surfaces differ. Everything from *The shared spine* onward is a programmer reference. Related: [[projectSpec]] for the module pipelines and API routes each chart reads from, and [`archive/graphEditor-overhaul.md`](../archive/graphEditor-overhaul.md) for why the editor was built the way it was before the surfaces split.

> [!important] One feature, two surfaces, one config
> `/[module]` and `/visualization-tool` look different and are aimed at different readers, but they are the same editor over the same declarative chart config, composing the same control sections. Any change to a section lands on both. When this document says "the editor", it means the shared machinery; when it says "the workbench" or "the wizard", it means one surface.

---

## What this is for

A PPIC researcher who wants a chart has two situations, and until 2026-07-28 the site treated them as one.

In the first, the data already exists on the site: population by county, components of change, RHNA progress. The researcher wants to look at it, change the geography, switch to percent change, and get a publishable image out. They have nothing to import and no reason to page through an import step to change a color.

In the second, the data is in a spreadsheet on their machine. They want to paste it, correct the inevitable header mess, bind columns to a chart, and export. Here a step sequence genuinely helps: import must come first, and chart type is a real decision made once.

Serving both from one step wizard meant the first researcher paid the second's costs. The surfaces now differ where the tasks differ and are identical everywhere else.

## The two surfaces

### The module workbench - `/[module]`

One screen. A control sidebar on the left, a chart container on the right, no navigation between them. Every control that applies to the current chart is visible at once; changing any of them re-renders the chart in place.

The sidebar sections, top to bottom: **Datasets**, **Chart Type**, **Outcome**, **Date Range**, **Geographic Level**, **Transform**, **Labels**, **Appearance**, **Typography**. A section that does not apply is absent, not empty - a module with one dataset has no Datasets block, and a scatter plot has no Transform block unless the module stratifies, in which case the block holds the pins and none of the radios.

**Nothing on this surface is chosen for the reader.** The workbench never binds a field on their behalf: it opens with every encoding unset, and switching chart type fills none in. The chart is a skeleton until the reader has set each required encoding themselves - see *The reader binds every field*. This is the one behavioral rule that separates the workbench from the wizard below the shell level, and it is why the workbench has no preset picker.

The chart container carries the module title, the chart, and an action bar: **View Chart | View Data** on the left, **Export Chart** and **Export Data** on the right.

### The standalone Visualization Tool - `/visualization-tool`

Four steps: **Import → Chart Type → Edit → Export**. Import is where a table is pasted, uploaded, and corrected; the other three steps are disabled until it holds data. The Edit step renders the same sections the workbench does, minus Chart Type, which is its own step.

The wizard also keeps four things the workbench deliberately drops:

| Kept here only | Why it does not belong on a module |
|---|---|
| **Presets** ("Trend over time", "Compare places") | A preset seeds a chart type and bindings from nothing. That is the opposite of the workbench's rule that no field is ever bound for the reader, and on a surface where every control is already visible a preset would silently overwrite choices they had made. |
| **Saved views** (save / restore / reset / config JSON) | Bring-your-own-data has no server dataset, so a saved view is the only way a chart survives a page refresh. A module chart is reproducible from its URL. |
| **Multi-chart workspace** (up to four charts, 2×2 layouts) | The workbench's whole premise is one chart with every control visible. Four charts in that space is a different product. |
| **Trace layers** ("Add line": benchmark, second source, second measure) | Layers are how a bring-your-own-data user compares two columns. On a module the same comparison is a Series binding or a Geographic Level selection. |
| **Activity log** | Records config imports and export failures - events that only occur on the wizard's surfaces. |

## The shared spine

Both shells mount the same three providers and pass the same config down.

```text
app/[module]/page.js                     app/visualization-tool/page.js
└── ModuleWorkbench                      └── VisualizationWizard
    └── ChartConfigProvider                  └── ChartConfigProvider
        └── PreviewProvider                      └── PreviewProvider
            ├── ViewHydrator                         ├── ViewHydrator
            ├── ModuleSidebar                        ├── StepNav + MultiChartToolbar
            │   └── SIDEBAR_SECTIONS                 └── ImportStep | ChartTypeStep
            └── ChartContainer                          | EditStep | ExportStep
                ├── PreviewPane (chart)                      └── SidebarSections
                ├── DataTableView (data)                         (exclude: chart-type)
                └── ChartContainerFooter
```

| Piece | File | Responsibility |
|---|---|---|
| `ChartConfigProvider` | `chart-builder/chartConfigStore.js` | The declarative config, inside a workspace, inside an undo/redo history. Every action re-runs validation. Takes `autoBind` - see *The reader binds every field*. |
| `PreviewProvider` | `chart-builder/wizard/PreviewContext.js` | Loads data for every chart slot, builds Plotly props, and holds the mounted graph div so exports come off the displayed figure. Takes `deferInitialRender` - see *Landing on a module builds nothing*. |
| `ViewHydrator` | `chart-builder/wizard/ViewHydrator.js` | Resolves `?view=` once on mount: a saved-view id, a serialized workspace, or a serialized single config. Shared so a link behaves the same wherever it is opened. |
| `SIDEBAR_SECTIONS` | `lib/visualization/sidebarSections.js` | The ordered section registry both shells compose from. |

### The section registry

A section is a `{ value, label, Component }` with at most two gates:

- **`key`** - the chart-type descriptor must list this key in its `sidebarSections`. This is "does this kind of chart use this control at all".
- **`when(config, schema)`** - a predicate for sections that depend on what the module supplies rather than on the chart type.

`visibleSectionsFor(config, schema, { only, exclude })` applies both and always returns registry order, so no caller can reorder the sidebar by argument order.

| Section | Component | Gate |
|---|---|---|
| Datasets | `sections/DatasetsSection.js` | `when: hasDatasetControls` - two or more datasets |
| Chart Type | `sections/ChartTypeSection.js` | always (excluded by the wizard, where it is a step) |
| Outcome | `sections/OutcomeSection.js` | `key: "encodings"` |
| Date Range | `sections/DateRangeSection.js` | `when: hasTemporalData` |
| Geographic Level | `sections/GeographySection.js` | `when: hasGeographicSubsets` |
| Transform | `sections/TransformSection.js` | `when: hasTransformControls` |
| Labels | `sections/LabelsSection.js` | `key: "labels"` |
| Appearance | `sections/AppearanceSection.js` | `key: "appearance"` |
| Typography | `sections/TypographySection.js` | `key: "appearance"` |

`sections/primitives.js` holds the heading, card, accordion wrapper, and boxed single-select list every section draws with. `sections/categoryControls.js` holds the row list and ranking controls that Geographic Level and Categories share.

> [!note] Categories is not in the registry
> `sections/CategoriesSection.js` - ordering, visibility, and Top-N for values that are not places - has no registry entry. `GeographySection` renders it when the chart type's categories are not geographic, and the wizard's Edit step renders it directly for bring-your-own-data, which has no geography at all. It is a fallback, not a section, so it never appears twice.

### Advanced Mode

A single switch above the sections on both surfaces - `ModuleSidebar` on the workbench, the Edit step's toolbar in the wizard - held by `components/chart-builder/advancedMode.js`. It is off on arrival and hides exactly one block today: **Ranked values** in Geographic Level and in Categories.

It is deliberately not the three-tier registry that preceded it (see *What was withdrawn*). There is no central table of what each tier hides; each section reads `useAdvancedMode()` and decides for itself, so the only way a control disappears is a line in the section that owns it. The flag is editor state, not chart state: it never reaches `config`, is not serialized into a saved view, and does not survive a reload.

> [!note] No switch on screen means nothing is hidden
> `useAdvancedMode()` outside a provider reports advanced. A control that no switch can reveal is a control nobody can reach, so a surface that mounts sections without the provider renders an extra block rather than losing one silently.

## The sidebar sections

### Datasets

One checkbox per dataset, **exclusive**: checking one unchecks the others, and clicking the checked one does nothing. Drawn as checkboxes to match the mockup, but a chart reads exactly one dataset, so the control writes the same single value a radio would.

Raw source ids are mapped to public names through `lib/visualization/datasetLabels.js` - `DoF` reads as "CA Department of Finance", `Census` as "US Census". The ids stay canonical in the config and the query string; only the label changes (guardrail #1).

That checkbox list is now the whole section, and Components of Change is the only module that shows it. The section is absent wherever a module offers fewer than two datasets, which after the July 2026 pass means everywhere else.

Two controls left the section, because "Datasets" was describing neither of them. **Data vintage** - Population & Housing's `E-5` / `E-8` / `Aggregated` multi-select - was per-row provenance on a module with exactly one dataset, and it defaulted to every vintage; it was removed rather than relocated, since an absent filter is what the API already reads as "all". **Stratification** (`schema.filterDimensions`: Age group, Sex, Race/ethnicity, Tenure, Income level) moved to Transform, where a control that changes which rows a measure is computed over belongs.

A third module withdrew its toggle without losing its sources. Age, Sex & Race Projections declares `datasets: []` while keeping `sources`, because the API pairs DoF P-3 with the California levels and Census cc-est with US States and rejects every other combination. The pairing is already enforced by `subsetSource` when a reader picks a geographic level, so the toggle offered a second, unguarded way to set the same value - and picking Census cc-est while sitting on Counties returned an error instead of a chart.

> [!important] One config key, two shapes
> `filters.source` still holds either a string (a dataset id) or an array (provenance labels), and `chartData.js`'s `sourceParams()` splits them back into the `source` and `sources` query params. Only the string shape has a control now; the array shape survives because `schema.provenanceFilter` still tells the data layer how to read Population & Housing's rows when a chart tabs by `Source`.

> [!note] The "Update data" button is unwired
> `schema.refreshable` no longer renders anything. `UpdateDataButton.js` and the `POST {apiPath}/update` routes are intact, but the button is disconnected until the server-side refresh pipeline is overhauled - a control that fires the old pipeline is worse than no control.

### Chart Type

A two-column grid of label tiles in a fixed design order: Line, Bar, Choropleth Map, Forest / Whisker Plot, Symbol Map, Dot Plot, Range, Pie / Donut, Scatter, Bubble, Matrix Heatmap, Data Table. The order is declared in the component, not read from the registry, because it is a design decision; any registered type missing from the list still renders, appended, so a new chart type is never silently unreachable.

Which of those tiles a given module actually offers is `isChartTypeAvailable(id, schema)` in `lib/visualization/chartAvailability.js`, the single owner of that question for both surfaces. It answers three things in order:

| Gate | Effect |
|---|---|
| `hidden` on the descriptor | Never offered. Today only the retired `divergingBar` id, kept registered so a bookmarked link still resolves through `RETIRED_CHART_TYPES` while Bar absorbs it as an `appearance.diverging` toggle. |
| `schema.supportedChartTypes` | Narrows the grid to an allowlist when a module declares one. RHNA Progress declares `["bar"]`. |
| `requiresGeometry` on the descriptor | A map type is offered only where something exists to join coordinates to: the level we hold geometry for on a module, or an inline shape builder on the standalone tool. See *Maps and geography*. |

The wizard's Chart Type step reads the same function, grouped into families (Line, Bar, Pie, Map, Range, Distribution, Table) rather than a flat grid. Unlike the workbench grid it has no append-the-forgotten fallback, so an id missing from `FAMILIES` simply does not appear there.

On the workbench a tile changes the chart type and nothing else. Encodings the new type can accept follow the reader across - a measure on Y stays on Y from a line to a bar - and every role the new type needs but did not inherit is left unset, **unless the new chart type implies it**: a line's X-Axis of `Year` does not become a bar's Category by carrying across, but a bar's Category resolves anyway, from the schema's geography field rather than from what the reader had bound. A role neither carried nor implied has no field chosen to stand in for it, so the container returns to the skeleton naming what is still to set. The wizard's Chart Type step behaves as it always has, seeding from the preset registry or, for bring-your-own-data, auto-mapping the pasted columns.

One thing besides the chart type does change on a tile click: selecting a map type also moves `filters.subset` to the level we hold geometry for, because that is a level, not a chart type.

### Outcome

A two-column grid of role dropdowns - **Series** and **Group**, followed by **Tab by column** - plus whichever of X-Axis/Category and Y-Axis the chart type has not already answered for itself. Roles otherwise come from the chart-type descriptor, so a forest plot asks for a study and its confidence bounds, and a dot plot asks for rows and series - the same control, relabelled.

The section sits directly after Chart Type, ahead of Date Range and Geographic Level. Outcome's dropdowns and its implied-role hints are answers *to* the chart type - which measure to plot, whether a bar diverges - so it reads better beside the control that decides it than after the two sections it merely references.

Each dropdown offers only fields whose `kind` satisfies the role's `roleConstraints`, and for measures also honours the field's own `chartRoles` catalog. Group additionally excludes high-cardinality fields and `Source`, which would produce one group per row.

#### No dropdown here says "Color"

The `color` role was two unrelated questions wearing one name, and the label answered neither of them well.

| Where `color` is constrained to | Chart types | What it does now |
|---|---|---|
| A **measure** | Choropleth Map, Matrix Heatmap | The colour *is* the plotted value, so the dropdown reads **Outcome**. Calling it "Color" asked for an outcome by naming the mechanism that draws it - the same mistake the implied-role reframe removed from the x and category axes. Dot Plot already labelled its own "Value" and keeps it. |
| A **dimension** | Line, Bar, Scatter, Bubble | Genuinely a colour choice, and rendered in Appearance beside the palette. `colorBindingSection: "appearance"` on those four descriptors (and on the hidden legacy Diverging Bar) declares the placement, so the control moves without changing `bindings.color`, its eligible fields, or the rendered chart. |

`roleLabel` reads the constraint rather than a list of ids, so a future chart type is labelled correctly without being added anywhere.

Two chart types declared the role and then ignored it, and both have dropped it outright rather than been relabelled: **Pie / Donut**, whose `pieSpec` colours each slice from the palette by its own category label - the slices already *are* the categories, so there was no second grouping to make - and **Symbol Map**, where every marker shares one palette colour. Binding a field in either changed nothing on screen.

Roles the reader never binds are also worth naming honestly. A symbol map's **Bubble value** used to read "Bubble size", borrowed from the bubble chart, where size genuinely is a third variable alongside x and y. On a map the marker areas are scaled from the measure and there is no size to pick, so the dropdown asks for the value being mapped.

Two deliberate departures from the old Encodings section: geography is gone (it belongs with the place selection it drives), and the **active preset's encoding list is no longer consulted**. Honouring it after a chart-type switch is what used to hide roles; roles now always come from the chart type.

On the workbench every dropdown starts on **Not set** and stays there until the reader picks. Required roles carry a red asterisk, and an unset one is not reported as an error anywhere - not in the sidebar, not in the container - because on a surface that binds nothing for you an empty required role is where every chart begins.

#### Implied roles

**A chart type may declare a role implied rather than bound.** A line's x is always the schema's one temporal field, and a bar's category is always its geographic level, so neither is offered as a dropdown. `lib/visualization/impliedRoles.js`'s `impliedBindings(chartTypeId, schema)` resolves both, strictly - a role the resolver cannot answer (an ambiguous temporal field, a schema with no geography) is omitted rather than guessed, and stays a real dropdown. The section renders the resolved role as a sentence instead - "Plotted against Year, set in Date Range", "One bar per location in Counties, set in Geographic Level" - naming the control that actually owns the setting, rather than as a disabled `Select` that would invite a click and explain nothing. Those two sections render *below* Outcome; the hint names them by label, not by position.

Folding an axis out of the grid also folds the question the reader is answering: with the category or x-axis already decided by chart type and context, the remaining measure role reads as **Outcome** rather than Y-Axis. `roleLabel` returns it for any chart type that declares an implied role at all, whether or not this schema resolves one, so bring-your-own-data's line still reads "Outcome" even though its X-Axis stays a real dropdown (it has no temporal field to imply from). This is what used to be two controls asking the same question twice: the duplicate Category dropdown here and the Geographic Level select below it. Removing it did not add a mapping table - a bar's category was always `Location` (`Jurisdiction` on RHNA Progress, by label only), the same column Geographic Level already filters.

`impliedRoles` is declared only on `line` and `bar` (and on the hidden `divergingBar` descriptor, which inherited the same entry). Scatter, bubble, heatmap, forest, and the Range family keep their full grid. `heatmap` declares `x: [TEMPORAL, DIMENSION]` and is deliberately left alone: its x is a real choice between two kinds.

> [!note] Implied is not auto-bound
> `withImpliedBindings` in `chartConfigStore.js` spreads the implied fields first and the reader's own bindings second, so an explicit choice - a saved view's `bindings.category`, a chart-type switch that carried a compatible field across - always wins. This looks like it violates *The reader binds every field*, but an implied role has exactly one valid answer, declared by the chart type, that the reader can see and change (by moving the Date Range slider or the Geographic Level select) - not a guess the editor made among several valid fields. `validateBindings` treats a resolved implied role the same way: never `MISSING_REQUIRED_ROLE`, because it was never unanswered. A chart type that declares a role implied but sits on a schema that cannot resolve it (checked via the resolved value, not the descriptor flag) still reports that role missing, because there it really is.

#### Orientation and Diverging bars

**Orientation is the one control the implied-role reframe keeps explicit.** Bar still offers a vertical/horizontal toggle here, beside the implied-role hint, because unlike category it is not inferable from anything already chosen elsewhere - a reader who wants a horizontal bar has to say so. A plain bar defaults vertical and a diverging one defaults horizontal, so turning Diverging on never changes orientation on its own: silently moving a control the reader can already see is precisely the auto-binding behaviour the workbench withdrew.

**A Diverging bars switch sits beside orientation, for `bar` only.** The retired `divergingBar` chart type is now `appearance.diverging` on a plain bar, writing `SET_APPEARANCE` / `diverging` and nothing else. Turning it on reveals Center reference and the rest of the dashboard-style controls in Appearance; turning it off hides them without touching orientation, the palette, or anything else the reader set. See *Bar absorbs Diverging Bar*.

### Date Range

A single- or dual-handle slider bounded by `schema.yearRange`, writing `period.year` or `period.startYear`/`endYear`. Dual for the chart types whose period is a span (line, heatmap, Range) and for bar/choropleth when a change transform makes them two-period. Absent for modules with no time axis - RHNA Progress declares no `yearRange` for exactly this reason.

### Geographic Level

The section that absorbed the most. A level `Select` over `schema.subsets` writes `filters.subset` and keeps the source side effects that pairing demands: a level with a `subsetSource` forces that source, and `States` forces Census where the module has it. A map-shaped chart is pinned to the one level we hold geometry for rather than offered levels that would render blank - the select narrows to that level, and the store has already written it (see *Maps and geography*).

Beneath it, a checkbox list of the individual places at that level - seven, then **Show more (N)**. Selection writes `filters.locations`; changing the level clears it, because a county name is not a region name and a stale filter would quietly match nothing.

Two controls sit above the list. A **search box** appears once the list is longer than the seven rows shown collapsed - five regions do not need a filter, five hundred cities are unusable without one. A **Select all** checkbox selects every row currently listed, and a **Clear (N)** button beside it drops the whole selection.

> [!note] "Select all" means "all of these matches"
> With a search active, Select all takes the filtered rows, not every location - a control sitting directly above a filtered list has to mean what the reader can see. **Clear** deliberately does the opposite and drops the entire selection, because a filtered clear would leave places selected that the reader cannot see to unselect. Reordering is also disabled while a search is active: an order written from the matches alone would silently drop every place the filter hid.

For chart types whose categories *are* places - line, bar, diverging bar - the same rows carry a drag handle and a visibility switch, writing `appearance.categoryOrder` and `appearance.hiddenCategories`, and the section also owns Top/Bottom N - behind **Advanced Mode**, the one block it hides. That is the point of folding them together: on a module, the things being ranked and the things being selected are the same list, and showing them as two lists of identical names was the confusion worth removing.

Every async state is named. Loading, "we could not load locations for this geographic level", and "no locations available for this geographic level" are three different sentences, because a failed request and an empty level are different problems.

> [!note] Empty means "let the ranking decide"
> `filters.locations: []` is not "no places". It means no explicit selection, so Top-N chooses. That is what lets a fresh chart draw something without the reader picking places one at a time, and it is why the key is omitted entirely from stored views when empty.

### Transform

Everything that changes what a measure says without changing which measure it is: how the values are expressed, and which slice of rows they are computed from.

Radio buttons over the bound measure's own `transforms` come first: Actual Value, Index to Base Year, Numeric Change, Percentage Change. A rate measure offers two options, not four - percent-of-a-percent is a category error, not a formatting choice, so a rate gets Percentage-Point Change instead.

Selecting Index to Base Year reveals a base-year `Select` bounded by `schema.yearRange`. It was a free number input before, which is how an out-of-range base year got in.

**Imported data gets the same section with two radios** - Absolute Values or Index to 100 at Base Period. A pasted table has no field catalog to read `transforms` from, so the pair is fixed: the two-period change transforms are computed by the module fetch layer (`chartData.js`), which has no inline equivalent. The base periods are the imported x column's own values, ascending, not a module year range; the wording says "period" rather than "year" because a pasted time axis is as often months, quarters, or waves. Left unset, the `Select` reads "First period in the data", which is exactly what `transformRegistry.js`'s base-value fallback does.

The pair is offered only where index-to-100 actually lands: a `transformCapable` chart type whose inline shape carries a time axis (line, heatmap) and whose table holds more than one period. A bar chart tags every inline row with one implied period, so indexing would set every category to 100 - the section stays absent rather than offering a radio the renderer ignores. `inlinePeriods(table, spec)` in `lib/tabular/toSeries.js` answers "which periods does this shape actually plot", parsing them exactly as the shape builders do so an offered period always matches a `years` entry the transform sees.

`transformOptions(config, schema)` in `lib/visualization/transformRegistry.js` owns both lists - `{ transforms, basePeriods, inline }` - so the section, its registry gate, and the reducer read one answer. The reducer's half is `withExpressibleTransform`, which runs on every revalidation and drops an *imported-data* transform the chart can no longer express: switching an indexed line to a bar, or re-importing a table that now holds a single period. A module keeps its stranded transform and surfaces `TRANSFORM_NOT_ALLOWED` instead, because there the field catalog is the reader's own to fix and a silent rewrite would hide the notice explaining it.

`validateBaseYear` exempts inline mode for the same reason the periods come from the table: an inline chart plots every row it was given, so the year slider's window is not its domain, and comparing the two would warn about a mismatch that does not exist.

Beneath them sit the module's **stratification pins**, one `Select` per entry in `schema.filterDimensions`, each defaulting to the precomputed aggregate row ("All Ages", "Both Sexes", "Total") rather than to no filter. They lived under Datasets until July 2026, which read as a claim they never made: choosing renters aged 65+ does not change which dataset you are reading, it changes which rows the measure is computed over - the same kind of statement the radios above make. Housing Stress and RHNA Progress are where the mismatch was most visible, since a dataset toggle is the one thing neither module has ever had.

The section returns nothing at all for chart types whose descriptor is not `transformCapable` - scatter, pie, the Range family - rather than rendering an empty block.

`hasTransformControls(config, schema)` is the exported form of that decision and the Transform entry's only gate. It deliberately carries no `key`: "comparison" was wrong twice over. Nearly every chart type declares it, including the ones that cannot transform, so `key` alone kept the accordion header and hid only its contents; and the stratification pins have to survive on the chart types that declare no comparison at all, because a data table of stratified rows still needs to say which rows.

The predicate answers in two steps. A schema with `filterDimensions` always has something to show, whatever the chart. Failing that, the transform radios need a `transformCapable` chart type **and** either more than one transform from `transformOptions` or a `benchmark` role to label. A lone "Actual Value" radio reads as a broken control, so it is never drawn - which is what keeps the section absent on a single-transform measure, and on imported data that has no second period to index against. The benchmark half is module-only: "Difference from Benchmark" fetches a module series, and an imported table has none. The section re-checks `transformCapable` internally for the same reason it always has: stratification alone can open it, and a scatter plot should gain the pins without gaining radios it cannot honour.

> [!note] The header is the thing that disappears
> Returning `null` from a section component only empties the accordion body; the trigger, its label, and the brand rule still render. A section that can render nothing therefore has to say so through the registry, not just through its own return value.

### Labels, Appearance, Typography

**Labels** is five text inputs - Title, Subtitle, X-Axis Label, Y-Axis Label, Legend Title - each placeholdered with the label the chart would derive from its bindings. Blank means "keep the derived label", which is why the derived text is a placeholder and not a pre-filled value: a derived title keeps tracking the data when a binding changes, a typed one deliberately stops.

**Appearance** opens with the optional **Color** field binding for Line, Bar, Scatter, and Bubble, followed by the five shared controls in order: Color Palette, Legend Position, Horizontal Line Spacing (px), Vertical Line Spacing (px), Footnote. The moved dropdown still writes `bindings.color`; Appearance owns only its location, not a new appearance property. Everything below Footnote is chart-type-conditional - markers, the diverging-bar dashboard styling, the forest plot's interval and marker styles, the colour scale, the watermark, the tooltip template. A default line chart therefore shows Color plus the five shared controls, and a diverging bar grows the ones it needs. Orientation lives in Outcome: it is the one degree of freedom bar still asks about explicitly, alongside the measure choice Outcome otherwise infers.

#### Bar absorbs Diverging Bar

Diverging Bar is not a chart type. It is `appearance.diverging` on a plain `bar` - a prop, not a component, the same way `pie` already varies through `hole`. The Center reference input and the dashboard-style controls (`DivergingStyleControls`: value-axis range, track rail, minimal axis, threshold colors) gate on `appearance.diverging` rather than on a chart type, so they appear the instant the reader flips the Diverging bars switch in Outcome and disappear the instant they flip it back - no chart-type switch, no lost bindings, no re-fetch.

`lib/visualization/toPlotly.js` routes on the same flag: a plain `bar` calls `barSpec`, a diverging one calls `divergingBarSpec`, and both draw from the identical `{category, value}` record contract the two renderers always shared - this was a router change, not a renderer change, and `toPlotly.catalog.test.js` asserts `{chartType: "bar", appearance: {diverging: true}}` renders byte-for-byte identically to the old `{chartType: "divergingBar"}` shape. `deriveLabels.js`'s `axisBindingNames` reads the same flag, so a diverging bar still derives diverging axis titles.

**The old id is retired, not deleted.** `lib/visualization/chartSpec.js`'s `RETIRED_CHART_TYPES` maps `divergingBar → bar`, and `normalizeSpec` rewrites a stored `divergingBar` view's `appearance` to `{ diverging: true, ...storedAppearance }` - the stored appearance spreads second, so `center`, `colorBuckets`, `valueRange`, `trackRail`, and `minimalAxis` all survive a migration untouched. `validateSpecShape` reports `CHART_TYPE_RETIRED` off the same map, so a re-saved bookmark quietly stops carrying the warning. The `divergingBar` descriptor itself stays registered in `chartRegistry.js` - marked `hidden: true` - so every code path that still reads `getChartType("divergingBar")` defensively keeps working; only the tile grid and the wizard gallery stop offering it, and `RHNA_PROGRESS_SCHEMA.supportedChartTypes` narrows to `["bar"]`.

> [!warning] The deferred deletion
> Deleting the `divergingBar` descriptor outright is the one step still outstanding, and it needs a release to pass first so a link saved the day before deletion still has something to resolve against. When it happens, seven sites go with it: the `case "divergingBar"` branches in `toPlotly.js`'s adapter switch and `valueAxisKeys`, `QUERY_SHAPES` in both `chartData.js` and `lib/tabular/toSeries.js`, `GROUP_SECTIONING_RECORD_CHARTS`, and the change-transform loader and series-name reader in `chartData.js`. All of them list `bar` and `divergingBar` together and treat them identically, so nothing is broken while they stay. The `RETIRED_CHART_TYPES` entry and its migration tests stay permanently: a bookmarked link is forever.

**Typography** is six numeric fields - title, subtitle, axis label, legend, and data label sizes, plus decimal places. Each clamps to its own range on the way into the config rather than trusting the input's `min`/`max`, which browsers enforce only on form submission.

## Maps and geography

Two chart types declare `requiresGeometry: true` - Choropleth Map and Symbol Map - and everything in this section exists because a chart type that needs coordinates is not like one that needs a column.

### One level, and the three decisions that follow

`AVAILABLE_GEO_LEVELS` in `lib/data/geography.js` is `["counties"]`. That single fact propagates through the editor as `GEOMETRY_SUBSET` in `lib/visualization/chartAvailability.js`, the schema-side name for the same level, and it decides three things.

| Decision | Owner | Behaviour |
|---|---|---|
| Is the tile offered at all? | `isChartTypeAvailable` | A map type appears only where `geometrySubsetFor(schema)` answers - so Building Permits (Metros, Regions, States) offers neither map tile, rather than tiles that could only ever fail at the data layer. |
| Which level does the chart sit on? | `withGeometrySubset` in `chartConfigStore.js` | Selecting a map type writes `filters.subset: "Counties"` and clears `filters.locations`, because a region name is not a county name and a carried-over selection would filter every row away. |
| Which levels does the select offer? | `GeographySection` | The level `Select` narrows to that one level, so the control agrees with the config the store just wrote. |

All three are needed, and the third alone is not enough: the level lives in `filters.subset`, and narrowing a select does not write it. A reader on Population & Housing lands on **Regions** by default, so pinning only the select left the config on Regions, sent `/api/geography?level=regions`, and failed the entire load with "Invalid 'level'. Expected one of: counties".

The standalone tool is gated by the same function on a different question. Pasted data has no server levels at all, so a map type is offered there only when `lib/tabular/toSeries.js` has an inline shape builder for it (`hasInlineShape`). A choropleth does; a symbol map does not, because a pasted table carries no coordinate contract to read lat/lon from. Symbol Map is therefore absent from the wizard's Map family rather than drawing an empty figure there.

### Where a symbol map's coordinates come from

A choropleth hands whole polygons to Plotly and lets it match by `featureidkey`. A symbol map needs one point per place, and no authoritative point file exists for any level. The points are **derived from the same polygons the choropleth draws**, in `lib/geography/representativePoint.js`:

| Step | Rule |
|---|---|
| Pick a part | A `Polygon` uses its own rings; a `MultiPolygon` uses its largest part by outer-ring area, so a mainland county with island parts never places its marker offshore. Three California counties (Los Angeles, Santa Barbara, Ventura) are MultiPolygons for this reason. |
| Try the centroid | The area-weighted centroid, accepted when it falls inside the part - inside the outer ring and outside every hole. |
| Otherwise scan | A horizontal scanline across every ring at the centroid's latitude, taking the midpoint of the widest inside interval under the even-odd rule. This is a simplified "point on surface", and it is what keeps a concave county's marker inside the county. Holes need no special case: their crossings join the same sorted list, and even-odd parity already treats the span across a hole as outside. |

A plain geometric centroid was rejected because a concave county can put it outside itself or offshore; a pole-of-inaccessibility calculation was rejected as more cost than the case needs. A point-file artifact stays explicitly deferred - it is the only option if a symbol ever needs to sit somewhere specific rather than at a shape's middle, and nothing today needs that. The module is client-safe (no `node:fs`) so it is unit-tested directly against synthetic fixtures rather than through the file-reading loader.

`lib/data/geography.js` owns the file read: `loadRepresentativePoints(level)` loads polygons through the existing `loadGeometry` and derives one `[lon, lat]` per feature, keyed by `GEOID`, cached in a `pointCache` parallel to the geometry cache.

### The route and the join

`/api/geography` grew a `type` param rather than a sibling route, because the two answers already shared level validation and `Cache-Control`: `type=polygons` (the default) returns the FeatureCollection, `type=points` returns `{ geoid: [lon, lat] }`. An unrecognised `type` is a 400 with a named source, like every other param.

`chartData.js` fetches it the way it fetches geometry - a `loadPoints`/`pointsCache` pair mirroring `loadGeometry`/`geometryCache` - and does the join itself, in `joinRecordsToPoints`. The join has to happen there rather than in `toPlotly.js`, and this is the one place a symbol map differs structurally from a choropleth: `SET_SERIES_COUNT`'s `geoUnmatched` is dispatched straight from `loadChartData`'s resolved `unmatched` array, before `toPlotly` is ever called from a render-time `useMemo` that has no path back to the reducer. A record whose `geoid` has no matching point is therefore dropped from the plotted series and its name appended to that same `unmatched` array, rather than left with `undefined` coordinates that would silently render one fewer marker. In practice the path is hard to reach for county data - the points are derived from the identical GeoJSON `queryGeoValues` uses to compute its own `unmatched` - but it is handled rather than assumed away.

`symbolMapSpec` in `toPlotly.js` needed no changes for the join: it already read plain `row.lat`/`row.lon`, which is the shape `chartData.js` now hands it.

> [!warning] A symbol map's measure is `size`, not `y`
> `chartData.js` builds a module request's `parameter` from the first bound measure role it finds. That chain read `y`, then `color`, then `start` - and a symbol map declares no `y` at all. Every symbol-map request therefore went out with no `parameter`, and every module API answered "Invalid or missing 'parameter'", which is the error a reader reported. `size` now sits in that chain, after `y`, so no chart type binding both changes which measure it asks for.

### What a symbol map looks like

`symbolMapSpec` draws one `scattergeo` trace, marker area proportional to the bound measure, over a **visible** base map: land, state boundaries, no frame, no coastline, transparent background, and `fitbounds: "locations"` so the frame lands on the places plotted rather than on the whole `usa` scope. A choropleth hides the base layers because its polygons *are* the map; a symbol map that hid them would be dots on a blank page with no way to tell where they are. The legend is off, because one unnamed trace carries every marker and a legend could only ever read "trace 0" - magnitude is in the marker areas.

Every marker takes the same colour, and that colour comes from the active palette through `seriesColor` rather than from a constant, so the Color Palette control in Appearance actually reaches this chart type. It is keyed on the bound measure, which also lets a per-series override in `appearance.seriesColors` name it - the same way the forest plot keys its single marker colour. This is why the chart type declares no `color` role: there is one colour, and the palette owns it.

> [!success] Verified end to end, in a browser
> `/api/geography?level=counties&type=points` returns 58 points, every one of them inside its own county - checked by point-in-polygon against the actual polygons, not just against California's bounding box. The live `geo` view returns 58 records all carrying `geoid`, and the join reports zero unmatched. `/pophousing` renders a county symbol map sized by total population, and the choropleth beside it is unchanged.

## The chart container

A single card: a centred, brand-underlined module title, a bordered body, and the action bar.

The body is the chart or the data behind it, chosen by a local `viewMode`. Chart mode is `PreviewPane`, with its full idle / unconfigured / loading / invalid / empty / error / ready vocabulary.

### Landing on a module builds nothing

A module page opens on a **skeleton** - the outline of the chart type currently selected, greyed and pulsing, under a prompt naming what to set - and issues **no data request at all**. The chart is built by the reader: the first change to any sidebar control arms the preview, and from then on it updates live on every change, chart-type switches included.

This is the `deferInitialRender` prop on `PreviewProvider`. The workbench opts in; the wizard leaves it off, because its Import step means the reader has already supplied data by the time a chart is on screen.

> [!note] Why the undo history is the arming signal
> "The reader changed something" is read from the store's `canUndo`, not from the request key. Undo history already excludes `COMPUTED_ACTIONS`, so the loader's own `SET_SERIES_COUNT` feedback cannot arm the chart and trigger the very fetch this defers. Keying off the request key instead would miss appearance-only changes, which do not alter the request. Arming is sticky: undoing back to the start leaves the chart rendered rather than blanking it.

Two cases opt back out, because in both the chart has already been asked for by name: an **iframe embed**, which has no sidebar to touch and would otherwise show a skeleton forever, and any **`?view=` deep link or saved view**, which names a specific chart. Both carry their own bindings, so both render immediately.

### The skeleton is the chart type

The skeleton used to draw seven vertical bars whatever was selected, which undercut its whole point: a reader building a line chart was shown a bar chart. Each descriptor now declares a `skeletonShape`, one of the ten names frozen in `chartRegistry.js`'s `SKELETON_SHAPES`.

| Shape | Chart types |
|---|---|
| `bars` | Bar (vertical, the default) |
| `barsHorizontal` | Bar, once the reader sets a horizontal orientation |
| `line` | Line |
| `gantt` | Range |
| `ganttNoAxes` | Forest / Whisker Plot |
| `scatter` | Scatter, Bubble, Dot Plot |
| `grid` | Matrix Heatmap |
| `map` | Choropleth Map, Symbol Map |
| `pie` | Pie / Donut |
| `table` | Data Table |

The shape lives on the descriptor rather than in a lookup table inside `PreviewPane.js` because every other per-type fact in this codebase does, and because `chartRegistry.catalog.test.js` can then fail a new chart type that forgets to declare one instead of letting it render silently as a bar. Bar is the only type whose shape depends on config as well as descriptor, so `skeletonShapeFor(chartType, appearance)` sits in `PreviewPane.js` beside the component that draws it, flipping `bars` to `barsHorizontal` on orientation and falling back to `bars` for an unregistered id rather than throwing.

Each non-map shape is a single oversized Lucide icon, tinted `text-muted-foreground/30` and thinned to `strokeWidth 1.25` because these render at roughly ten times their design size, where an unscaled stroke reads as a heavy blob. The `map` shape is the exception and draws `components/charts/CaliforniaCountiesOutline.js` - all 58 county paths - because no icon set has California and a generic pin would say less than the silhouette does. Data Table declares a shape it never shows: with no required roles it is never unconfigured, so it fetches immediately.

> [!important] What the skeleton must not change
> The `role="status"` wrapper, its `aria-label`, the `aria-hidden` on the decorative interior, and the `min-h-72` floor are byte-identical to the bars version. `ChartContainer` measures this body to pin the data view to the same height, and re-measures on every preview-status change, so a shape reporting a different height would move the sidebar beside it on every toggle.

### The two views are the same height

The body is free-height in chart mode, governed by its `min-h-130` floor; on the way into data mode its rendered height is measured and pinned inline, and the table is bounded by that box rather than allowed to grow. Without this the data view - 50 rows to a page - made the card taller, and because the workbench's grid row takes its height from this container alone, the sidebar beside it stretched too, so every toggle moved the whole page.

The height is measured rather than declared as a constant, because the chart view's own height depends on the chart type: PreviewPane's floor, or the taller of the plot, its border and its tab row. Where nothing can be measured the CSS floor stands in.

**Data mode shows the entire cleaned dataset** - every row and every column of the module's CSV, via `?view=table&full=1`, not the narrowed table the chart draws. A reader who switches to the data is asking what is in the file; the chart's own columns are already visible as the chart. It is fetched lazily on first open and cached for the session, and the hook lives in `ChartContainer` rather than in the table so the load survives toggling back to the chart. Loading, error, and empty are named states, like everywhere else data is fetched.

`ChartContainerFooter` carries the View Chart | View Data toggle and the two export dropdowns. It takes preview state as props rather than calling `usePreview()`, which keeps it a presentational bar that can mount anywhere.

Both dropdowns are told whether the preview is `ready`, and they act on it differently:

| | Not ready |
|---|---|
| **Export Chart** | Disabled outright. Image export runs off the mounted graph div, and there is no figure. |
| **Export Data** | Open. Its **Original data (entire cleaned dataset)** items are addressed by `?view=table&full=1` from config and schema alone, so they never needed a rendered chart; only the **Chart data (as displayed)** items grey out. |

That distinction matters more now that a module opens unarmed: the dataset is the thing a researcher most often wants, and making them build a chart first to get a CSV they were not going to look at is a toll. The trigger closes only when neither source has anything to write.

`ExportMenu.js` exports `ExportChartButton` and `ExportDataButton` separately for this reason; its default export composes both with the image-quality control for the wizard's Export step.

### The reader binds every field

Arming the preview is not the same as having a chart to draw. The workbench passes `autoBind={false}` to `ChartConfigProvider`, and that one flag is the whole manual-encoding rule:

| Where | With `autoBind` (the wizard) | Without it (the workbench) |
|---|---|---|
| Opening the editor | The default preset seeds a chart type and its bindings. | Chart type only; `bindings` holds nothing **except an implied role the chart type resolves** - a line opens with `x: "Year"` already set, from the schema alone, not from the preset. |
| `SET_CHART_TYPE` | `bindingsForPreset` carries compatible bindings **and** fills the rest from the preset defaults and the field catalog. | `carriedBindings` carries the compatible ones and stops. Roles the new type does not declare fall away; roles it needs and did not inherit stay unset - **unless the new type implies one**, in which case `withImpliedBindings` resolves it regardless of `autoBind`. |
| A required role left unset | An error, reported in the sidebar and blocking the preview. | Neither. The preview reports `unconfigured` and draws the skeleton. An implied-and-resolved role is never in this row at all - it was never unset. |

The skeleton names the gap rather than only reporting one: `unsetRoles` reads the roles out of the validation findings, so the caption reads "Set X-Axis and Y-Axis to build this chart" for a scatter (neither axis implied) or "Set Outcome to build this chart" for a line or bar, falling back to the generic prompt when no finding carries a role.

> [!note] Unfinished is not invalid
> `MISSING_REQUIRED_ROLE` and `MISSING_PRESET_ROLE` are still error-level findings - a chart with no Y-axis cannot be drawn, exported, or saved as a view, and `hasBlockingErrors` is unchanged, so `savedViews.js` still refuses one. What changed is who treats them as a fault. `validation.js` names them in `INCOMPLETE_CODES`, and the two surfaces that speak to the reader - `ValidationNotice` and `PreviewPane` - suppress them where nothing is auto-bound. Every other error, including one the reader can actually cause (a source not chosen, a level a map cannot draw), reports exactly as before.

Two consequences are worth stating plainly. **No request goes out for a half-set chart**: `isUnconfigured` short-circuits the load effect, so a chart-type switch that leaves a role empty costs nothing and cannot surface a server error for a question the reader never asked. And **the skeleton wins the frame**: the unconfigured verdict is computed ahead of any preview state the load effect has yet to overwrite, so clearing a binding shows the skeleton on the same commit rather than flashing the previous chart until the effect catches up.

Bring-your-own-data is deliberately outside all of this. It auto-maps pasted columns onto roles by name and type, `inlineRenderBlock` already explains an unmappable table in its own words, and an unset role there is a dead end rather than a step not yet taken.

## The data views

`chartData.js` is the only place the browser talks to a module API. It maps chart type to a query "view" - the server never sees "chart type", only a data-shape verb - and builds the query string.

| View | Shape | Used by |
|---|---|---|
| `line` | `{ series: [{ location, years[], values[] }] }` | line |
| `category` | `{ period, records: [{ location, category, value }] }` | bar, diverging bar, pie |
| `twoPeriod` | `{ startYear, endYear, records: [{ category, start, end }] }` | Range, forest |
| `pairs` | `{ period, records: [{ location, x, y, size? }] }` | scatter, bubble |
| `matrix` | `{ matrix: { x, y, z } }` | heatmap, dot plot |
| `geo` | `{ records: [{ location, category, value, geoid }], unmatched }` | choropleth (joined to polygons by Plotly) and symbol map (joined to derived points in `chartData.js`) |
| `table` | every column of the cleaned CSV | data table, dataset export |
| `locations` | `{ locations: string[], subset: string }` | the geographic multi-select |

The `geo` view is the only one that needs a second request. Polygons and derived points both come from `/api/geography` (`type=polygons` / `type=points`), described under *Maps and geography*.

### `view=locations`

Every module route accepts `?view=locations&subset=<subset>` and answers with exactly `{ locations: string[], subset: string }` - nothing else, because the multi-select needs nothing else. It resolves **before** each route's measure and period validation, since it carries neither.

Each module resolves its own subset rows first and hands them to the shared `buildLocationList`, which does no level filtering of its own. That matters because the resolution differs per module: Building Permits aggregates metros into regions and invents a "Rest of US" row, and RHNA Progress reads `Jurisdiction` rather than `Location`.

`useLocationOptions(schema, filters)` consumes it, cached per module + subset in a module-level `Map` so re-opening a level never re-fetches, and aborting in flight so dragging through levels cannot let a slow earlier response overwrite a newer list.

## Config migrations

Four shapes changed. All four are handled on load, because a bookmarked `?view=` link must not break when a control retires.

| Change | Handling |
|---|---|
| `filters.locations` added | `normalizeSpec` lifts a legacy `selectedPlaces` layer's values into it, leaving the layer alone - the standalone tool still renders from it. Omitted entirely when empty. |
| `tier` removed | Listed in `RETIRED_KEYS` and stripped on normalize. `SET_TIER` is deliberately unhandled by the reducer, so old code dispatching it changes nothing rather than reintroducing the key. |
| `chartType: "slope"` retired | `RETIRED_CHART_TYPES` maps it to `line`; `parseSpec` reports a `CHART_TYPE_RETIRED` warning so the change is visible rather than silent. |
| `chartType: "divergingBar"` retired | `RETIRED_CHART_TYPES` maps it to `bar`, and `normalizeSpec` rewrites the appearance to `{ diverging: true, ...stored }` so the center reference and dashboard styling survive verbatim. See *Bar absorbs Diverging Bar*. |

> [!danger] The retirement hook is in `normalizeSpec`, not `migrateSpec`
> `migrateSpec` returns early for any spec already at `SPEC_VERSION`, and every stored view written since the v2 cutover is. A retirement written into `migrateSpec` would therefore run for no real stored view while passing its unit test on a hand-written v1 fixture. Both retirements live in `normalizeSpec`, beside the `RETIRED_CHART_TYPES` lookup.

`SPEC_VERSION` stayed at 2 throughout: nothing about the wire shape became unreadable.

## What was withdrawn, and why

| Withdrawn | Reasoning |
|---|---|
| **Settings tiers** (Basic / Moderate / Advanced) | The tiers hid controls the sections already gate by chart type and schema, from a central registry no section owned. In practice the second gate rarely helped and regularly hurt: a user told about a control could not find it. A single Advanced Mode switch returned on 2026-07-30, but without the registry: one boolean, and each section decides for itself what it hides. Today only Ranked values does. |
| **Code editor** (GUI ⇄ Spec / R / Stata) | The parsers recognised only the subset the generator emitted, so hand-written code surfaced as `CODE_UNSUPPORTED` warnings and the honest guidance was "use the GUI". The **generators** (`codebridge/{grammar,toRCode,toStataCode}.js`) were kept, dormant and tested, against a future "copy the code for this chart" export item. |
| **Slopegraph** | Duplicated the Range chart: both were two-period views of one measure, and a line renders the same bindings. |
| **The View Data step** | Its three modes became one toggle plus one export item; the middle mode (full-width but filtered) was the least used and was dropped. |
| **Diverging Bar as a chart type** | Same roles, same constraints, same record contract as Bar; only the anchor differs. It is a prop now. See *Bar absorbs Diverging Bar*. |
| **The duplicate Category dropdown** | A bar's category was always the same column Geographic Level already filtered, so the grid asked one question twice. See *Implied roles*. |
| **Symbol Map on pasted data, and both map types on Building Permits** | Neither surface had anything to join coordinates to, so the tiles could only ever produce an empty figure or a failed request. See *Maps and geography*. |
| **The `color` role on Pie / Donut and Symbol Map** | Both declared it and neither renderer read it: a pie colours its slices by their own category label, and a symbol map gives every marker one palette colour. A dropdown that changes nothing is worse than no dropdown. See *No dropdown here says "Color"*. |
| **Presets, saved views, multi-chart, layers, activity log** - *from modules only* | See *The two surfaces*. All five remain on the standalone tool. |

Everything withdrawn is recorded in `.trash/`, with the reasoning and enough detail to restore it.

## Testing

Tests live under `tests/js/`, mirroring the source path, and run under Vitest with `@testing-library/react`. Four conventions apply.

**Assert on behavior, not markup.** Query by role, label, and accessible name. The one deliberate exception is `ModuleSidebar.layout.test.js`, which asserts CSS classes because the positioning *is* the behavior and jsdom cannot lay out.

**Every async boundary gets three tests** - loading, error, and success. `useLocationOptions` and the location picker are the main ones.

**Migration tests are not optional.** Each config-shape change round-trips an old stored view. A user with a bookmarked link is the regression these catch.

**A test must be able to fail.** Expectations are hand-written rather than read back from the thing under test: `PreviewPane.skeleton.test.js` keeps its own `EXPECTED_SHAPE` map, asserted to cover `CHART_TYPE_IDS` exactly, instead of asking the registry what it declared and then agreeing with the answer. Module-level caches (`pointsCache`, `geometryCache`) are re-imported per test for the same reason - a second test served from the first test's cache is not exercising the fetch it appears to.

Three architecture tests keep the removals and the wiring honest: `architecture/moduleWorkbench.removals.test.js` fails if any file under `app/`, `components/`, or `lib/` imports the settings-tier gate or the codebridge; `ModuleSidebar.composition.test.js` fails if a wizard-only control is wired into the module rail; and `architecture/geometryLoaders.test.js` fails if a chart type declares `requiresGeometry` without a matching loader branch in `chartData.js`. The third was written against the exact bug it guards - Symbol Map was registered, given a Plotly adapter, and put on the tile grid before any loader existed for it - and was confirmed to fail against a deliberately unwired build before being trusted.

The manual-encoding rule is tested at each of its three layers, and each layer also asserts the auto-binding surface is untouched. `chartConfigStore.test.js` covers the store (opens with its implied roles resolved and nothing else, honours a view's bindings and lets one override an implied role, carries only what the new chart type accepts on a switch while still resolving what it implies, and moves a map chart to the geometry level without disturbing a non-map one); `wizard/PreviewContext.unconfigured.test.js` runs the real store against the real `pophousing` schema and asserts that an unset role fetches nothing, that setting the last one renders, and that a bar reached from a line renders on its implied category rather than returning to `unconfigured`; `wizard/PreviewPane.skeleton.test.js` and `ValidationNotice.test.js` cover what the reader sees, including that an unset role produces no alert. `impliedRoles.test.js`, `chartAvailability.test.js`, and `chartRegistry.catalog.test.js` cover the registries themselves.

## Settled since the split

**Should a chart-type switch keep drawing a chart?** No - settled 2026-07-29. Switching chart types re-seeded every unfilled role from the preset defaults, so a reader clicking through the tiles was shown a succession of charts nobody had asked for, and the roles that could not be seeded were reported as configuration errors instead. The workbench now binds nothing on the reader's behalf and shows the skeleton until each encoding is set. See *The reader binds every field*.

**Does the location multi-select need search?** Yes - added 2026-07-28, along with Select all / Clear. Seven-plus-Show-more was fine for nine regions and workable for fifty-eight counties, but not for the roughly five hundred cities Population & Housing carries. See *Geographic Level*.

**Should the Axis section ask for a role the chart type has already decided?** No - settled 2026-07-30. A line's x is always the schema's one temporal field and a bar's category is always its geographic level, so asking for both was one question asked twice - once in the Axis grid, once in Geographic Level - and the duplicate Category dropdown was a symptom of the same mistake, not a separate one. The section is now **Outcome**, a chart type may declare a role implied, and `impliedRoles.js` resolves it from the schema rather than from a dropdown. Three sub-questions settled with it: the reframe applies to line and bar only; a bar on a module with no geography falls back to a real dropdown rather than erroring at schema time; and the wizard gets the reframe unconditionally, since bring-your-own-data resolves neither role and only the Y label changes there.

**Does Bar absorbing Diverging Bar change what a diverging chart looks like?** No - settled 2026-07-30. `appearance.diverging` routes through the exact same `divergingBarSpec` renderer the chart type always called, so nothing about how a diverging bar draws changed - only how a reader turns one on and what the stored config calls it. A stored `divergingBar` view migrates automatically, with its center reference and dashboard styling intact, and a `CHART_TYPE_RETIRED` warning names what changed.

**Does turning on Diverging change orientation?** No - settled 2026-07-30. The reader owns orientation directly after the Outcome reframe, and silently moving a control they can see is the auto-binding behaviour the workbench withdrew. `divergingBar`'s horizontal default became a preset concern rather than a switch side effect.

**Should the skeleton show the chart type being built?** Yes - settled 2026-07-30. A reader building a line chart was shown seven bars. Every descriptor now declares a `skeletonShape`, and the catalog test fails a chart type that forgets one. See *The skeleton is the chart type*.

**Centroids or a point file for the symbol map?** Neither, exactly - settled 2026-07-31. A representative point derived from the existing county polygons: an area-weighted centroid where that lands inside the shape, a scanline interior point where it does not. This avoids a plain centroid landing outside a concave county or offshore without taking on a new data artifact or pipeline step. A point file stays deferred against the case where a symbol must sit somewhere specific. See *Maps and geography*.

**Should a dropdown be called "Color"?** Only where it chooses colours - settled 2026-07-31. On a choropleth or a heatmap the colour is the plotted value, so that dropdown reads **Outcome**; on Pie / Donut and Symbol Map the role was declared and never read, so it is gone; on the four chart types where it groups a dimension it stays, in Appearance beside the palette. A symbol map's measure role was renamed with it, from "Bubble size" to **Bubble value**, since the marker areas are scaled from the measure rather than chosen. See *No dropdown here says "Color"*.

**Should a chart type be offered where it cannot draw?** No - settled 2026-07-31. Symbol Map was reachable on every module and on the standalone tool before any coordinates existed for it, and both map types stayed reachable on Building Permits, which has no level we hold geometry for. Availability is now one function both galleries read, and an architecture test fails a future map type that repeats the pattern. See *Maps and geography*.

## Open questions

**Should the R/Stata generators come back as an export item?** They are kept and tested but unreachable. Either wire them into the Export Chart menu or delete all three files with their tests; leaving them dormant indefinitely is the worst of both.

**Does the Datasets section eventually merge dataset and provenance?** The mockup drew three checkboxes - "CA Department of Finance", "US Census", "Aggregated" - mixing a dataset toggle with a provenance value. They are two controls today. If a module ever needs both at once, that assumption is the first thing to revisit.

**Does a symbol map ever need a marker somewhere other than the shape's middle?** A derived representative point answers "which county is this" correctly and says nothing about where within the county anything actually is. The point-file option under *Maps and geography* is the answer if that distinction ever starts to matter; nothing today needs it.

**Should pasted data be able to draw a symbol map?** It would need a coordinate contract - two named columns bound to lat and lon, or a geography column joined to a server lookup. Neither exists, so the tile is simply absent from the standalone tool rather than drawing an empty figure.

**When does the `divergingBar` descriptor get deleted?** One release after the migration shipped, per the deferred-deletion warning under *Bar absorbs Diverging Bar*. The seven remaining read sites are listed there.
