# Visualization Specification

> [!info] Who this document is for and how to read it
> This is an **as-built specification** - everything described here is shipped. The first two sections are for anyone: what the feature is for, and how the two surfaces differ. Everything from *The shared spine* onward is a programmer reference. Related: [[projectSpec]] for the module pipelines and API routes each chart reads from, and [`archive/graphEditor-overhaul.md`](../archive/graphEditor-overhaul.md) for why the editor was built the way it was before the surfaces split.

> [!important] One feature, two surfaces, one config
> `/[module]` and `/visualization-tool` look different and are aimed at different readers, but they are the same editor over the same declarative chart config, composing the same control sections. Any change to a section lands on both. When this document says "the editor", it means the shared machinery; when it says "the workbench" or "the wizard", it means one surface.

---

## What this is for

A PPIC researcher who wants a chart has two situations, and until 2026-07-28 the site treated them as one.

In the first, the data already exists on the site: population by county, components of change, RHNA progress. The researcher wants to look at it, change the geography, switch to percent change, and get a publishable image out. They have nothing to import and no reason to page through an import step to change a color.

In the second, the data is in a spreadsheet on their machine. They want to paste it, correct the inevitable header mess, bind columns to a chart, and export. Here a step sequence genuinely helps: import must come first, and chart type is a real decision made once.

Serving both from one step wizard meant the first researcher paid the second's costs. The surfaces now differ where the tasks differ and are identical everywhere else.

## The two surfaces

### The module workbench - `/[module]`

One screen. A control sidebar on the left, a chart container on the right, no navigation between them. Every control that applies to the current chart is visible at once; changing any of them re-renders the chart in place.

The sidebar sections, top to bottom: **Datasets**, **Chart Type**, **Outcome**, **Date Range**, **Geographic Level**, **Transform**, **Labels**, **Appearance**, **Typography**. A section that does not apply is absent, not empty - a module with one dataset has no Datasets block, and a scatter plot has no Transform block unless the module stratifies, in which case the block holds the pins and none of the radios.

**Nothing on this surface is chosen for the reader.** The workbench never binds a field on their behalf: it opens with every encoding unset, and switching chart type fills none in. The chart is a skeleton until the reader has set each required encoding themselves - see *The reader binds every field*. This is the one behavioral rule that separates the workbench from the wizard below the shell level, and it is why the workbench has no preset picker.

The chart container carries the module title, the chart, and an action bar: **View Chart | View Data** on the left, **Export Chart** and **Export Data** on the right.

### The standalone Visualization Tool - `/visualization-tool`

Four steps: **Import → Chart Type → Edit → Export**. Import is where a table is pasted, uploaded, and corrected; the other three steps are disabled until it holds data. The Edit step renders the same sections the workbench does, minus Chart Type, which is its own step.

The wizard also keeps four things the workbench deliberately drops:

| Kept here only | Why it does not belong on a module |
|---|---|
| **Presets** ("Trend over time", "Compare places") | A preset seeds a chart type and bindings from nothing. That is the opposite of the workbench's rule that no field is ever bound for the reader, and on a surface where every control is already visible a preset would silently overwrite choices they had made. |
| **Saved views** (save / restore / reset / config JSON) | Bring-your-own-data has no server dataset, so a saved view is the only way a chart survives a page refresh. A module chart is reproducible from its URL. |
| **Multi-chart workspace** (up to four charts, 2×2 layouts) | The workbench's whole premise is one chart with every control visible. Four charts in that space is a different product. |
| **Trace layers** ("Add line": benchmark, second source, second measure) | Layers are how a bring-your-own-data user compares two columns. On a module the same comparison is a Series binding or a Geographic Level selection. |
| **Activity log** | Records config imports and export failures - events that only occur on the wizard's surfaces. |

## The shared spine

Both shells mount the same three providers and pass the same config down.

```text
app/[module]/page.js                     app/visualization-tool/page.js
└── ModuleWorkbench                      └── VisualizationWizard
    └── ChartConfigProvider                  └── ChartConfigProvider
        └── PreviewProvider                      └── PreviewProvider
            ├── ViewHydrator                         ├── ViewHydrator
            ├── ModuleSidebar                        ├── StepNav + MultiChartToolbar
            │   └── SIDEBAR_SECTIONS                 └── ImportStep | ChartTypeStep
            └── ChartContainer                          | EditStep | ExportStep
                ├── PreviewPane (chart)                      └── SidebarSections
                ├── DataTableView (data)                         (exclude: chart-type)
                └── ChartContainerFooter
```

| Piece | File | Responsibility |
|---|---|---|
| `ChartConfigProvider` | `chart-builder/chartConfigStore.js` | The declarative config, inside a workspace, inside an undo/redo history. Every action re-runs validation. Takes `autoBind` - see *The reader binds every field*. |
| `PreviewProvider` | `chart-builder/wizard/PreviewContext.js` | Loads data for every chart slot, builds Plotly props, and holds the mounted graph div so exports come off the displayed figure. Takes `deferInitialRender` - see *Landing on a module builds nothing*. |
| `ViewHydrator` | `chart-builder/wizard/ViewHydrator.js` | Resolves `?view=` once on mount: a saved-view id, a serialized workspace, or a serialized single config. Shared so a link behaves the same wherever it is opened. |
| `SIDEBAR_SECTIONS` | `lib/visualization/sidebarSections.js` | The ordered section registry both shells compose from. |

### The section registry

A section is a `{ value, label, Component }` with at most two gates:

- **`key`** - the chart-type descriptor must list this key in its `sidebarSections`. This is "does this kind of chart use this control at all".
- **`when(config, schema)`** - a predicate for sections that depend on what the module supplies rather than on the chart type.

`visibleSectionsFor(config, schema, { only, exclude })` applies both and always returns registry order, so no caller can reorder the sidebar by argument order.

| Section | Component | Gate |
|---|---|---|
| Datasets | `sections/DatasetsSection.js` | `when: hasDatasetControls` - two or more datasets |
| Chart Type | `sections/ChartTypeSection.js` | always (excluded by the wizard, where it is a step) |
| Outcome | `sections/OutcomeSection.js` | `key: "encodings"` |
| Date Range | `sections/DateRangeSection.js` | `when: hasTemporalData` |
| Geographic Level | `sections/GeographySection.js` | `when: hasGeographicSubsets` |
| Transform | `sections/TransformSection.js` | `when: hasTransformControls` |
| Labels | `sections/LabelsSection.js` | `key: "labels"` |
| Appearance | `sections/AppearanceSection.js` | `key: "appearance"` |
| Typography | `sections/TypographySection.js` | `key: "appearance"` |

`sections/primitives.js` holds the heading, card, accordion wrapper, and boxed single-select list every section draws with. `sections/categoryControls.js` holds the row list and ranking controls that Geographic Level and Categories share.

> [!note] Categories is not in the registry
> `sections/CategoriesSection.js` - ordering, visibility, and Top-N for values that are not places - has no registry entry. `GeographySection` renders it when the chart type's categories are not geographic, and the wizard's Edit step renders it directly for bring-your-own-data, which has no geography at all. It is a fallback, not a section, so it never appears twice.

### Advanced Mode

A single switch above the sections on both surfaces - `ModuleSidebar` on the workbench, the Edit step's toolbar in the wizard - held by `components/chart-builder/advancedMode.js`. It is off on arrival and hides exactly one block today: **Ranked values** in Geographic Level and in Categories.

It is deliberately not the three-tier registry that preceded it (see *What was withdrawn*). There is no central table of what each tier hides; each section reads `useAdvancedMode()` and decides for itself, so the only way a control disappears is a line in the section that owns it. The flag is editor state, not chart state: it never reaches `config`, is not serialized into a saved view, and does not survive a reload.

> [!note] No switch on screen means nothing is hidden
> `useAdvancedMode()` outside a provider reports advanced. A control that no switch can reveal is a control nobody can reach, so a surface that mounts sections without the provider renders an extra block rather than losing one silently.

## The sidebar sections

### Datasets

One checkbox per dataset, **exclusive**: checking one unchecks the others, and clicking the checked one does nothing. Drawn as checkboxes to match the mockup, but a chart reads exactly one dataset, so the control writes the same single value a radio would.

Raw source ids are mapped to public names through `lib/visualization/datasetLabels.js` - `DoF` reads as "CA Department of Finance", `Census` as "US Census". The ids stay canonical in the config and the query string; only the label changes (guardrail #1).

That checkbox list is now the whole section, and Components of Change is the only module that shows it. The section is absent wherever a module offers fewer than two datasets, which after the July 2026 pass means everywhere else.

Two controls left the section, because "Datasets" was describing neither of them. **Data vintage** - Population & Housing's `E-5` / `E-8` / `Aggregated` multi-select - was per-row provenance on a module with exactly one dataset, and it defaulted to every vintage; it was removed rather than relocated, since an absent filter is what the API already reads as "all". **Stratification** (`schema.filterDimensions`: Age group, Sex, Race/ethnicity, Tenure, Income level) moved to Transform, where a control that changes which rows a measure is computed over belongs.

A third module withdrew its toggle without losing its sources. Age, Sex & Race Projections declares `datasets: []` while keeping `sources`, because the API pairs DoF P-3 with the California levels and Census cc-est with US States and rejects every other combination. The pairing is already enforced by `subsetSource` when a reader picks a geographic level, so the toggle offered a second, unguarded way to set the same value - and picking Census cc-est while sitting on Counties returned an error instead of a chart.

> [!important] One config key, two shapes
> `filters.source` still holds either a string (a dataset id) or an array (provenance labels), and `chartData.js`'s `sourceParams()` splits them back into the `source` and `sources` query params. Only the string shape has a control now; the array shape survives because `schema.provenanceFilter` still tells the data layer how to read Population & Housing's rows when a chart tabs by `Source`.

> [!note] The "Update data" button is unwired
> `schema.refreshable` no longer renders anything. `UpdateDataButton.js` and the `POST {apiPath}/update` routes are intact, but the button is disconnected until the server-side refresh pipeline is overhauled - a control that fires the old pipeline is worse than no control.

### Chart Type

A two-column grid of label tiles in a fixed design order: Line, Bar, Choropleth Map, Forest / Whisker Plot, Symbol Map, Dot Plot, Range, Pie / Donut, Scatter, Bubble, Matrix Heatmap, Data Table. The order is declared in the component, not read from the registry, because it is a design decision; any registered type missing from the list still renders, appended, so a new chart type is never silently unreachable - **except a `hidden` descriptor**, added for the retired `divergingBar` id (Workstream B, 2026-07-30): Bar absorbs it as an `appearance.diverging` toggle in Outcome rather than a second tile, so the id stays registered for one release (so a bookmarked link still resolves) but does not reappear as an orphaned tile. `schema.supportedChartTypes` narrows the grid for modules that support only some.

On the workbench a tile changes the chart type and nothing else. Encodings the new type can accept follow the reader across - a measure on Y stays on Y from a line to a bar - and every role the new type needs but did not inherit is left unset, **unless the new chart type implies it** (Workstream A): a line's X-Axis of `Year` does not become a bar's Category by carrying across, but a bar's Category resolves anyway, from the schema's geography field rather than from what the reader had bound. A role neither carried nor implied has no field chosen to stand in for it, so the container returns to the skeleton naming what is still to set. The wizard's Chart Type step behaves as it always has, seeding from the preset registry or, for bring-your-own-data, auto-mapping the pasted columns.

### Outcome

> [!note] Moved here from after Geographic Level
> An audit follow-up (2026-07-30) moved this section to directly follow Chart Type, ahead of Date Range and Geographic Level. Outcome's remaining dropdowns and its implied-role hints are answers *to* the chart type - which measure to plot, whether a bar diverges - so the section reads better beside the control that decides it than after the two sections it merely references. `sidebarSections.js`'s registry order is the only thing that changed; no component, gate, or behavior moved.

A two-column grid of role dropdowns - **Series** and **Group**, followed by **Tab by column** - plus whichever of X-Axis/Category and Y-Axis the chart type has not already answered for itself. **Color** remains a binding, but Line, Bar, Scatter, and Bubble render that dropdown in Appearance beside the palette; chart types outside those four keep it here in Outcome. The placement is declared by `colorBindingSection: "appearance"` on those four active chart-type descriptors (and the hidden legacy Diverging Bar descriptor), so the control moves without changing `bindings.color`, its eligible fields, or the rendered chart. Roles otherwise come from the chart-type descriptor, so a forest plot asks for a study and its confidence bounds, and a dot plot asks for rows and series - the same control, relabelled.

Each dropdown offers only fields whose `kind` satisfies the role's `roleConstraints`, and for measures also honours the field's own `chartRoles` catalog. Group additionally excludes high-cardinality fields and `Source`, which would produce one group per row.

Two deliberate departures from the old Encodings section: geography is gone (it belongs with the place selection it drives), and the **active preset's encoding list is no longer consulted**. Honouring it after a chart-type switch is exactly what hid roles in flagged issue 2; roles now always come from the chart type.

On the workbench every dropdown starts on **Not set** and stays there until the reader picks. Required roles carry a red asterisk, and an unset one is not reported as an error anywhere - not in the sidebar, not in the container - because on a surface that binds nothing for you an empty required role is where every chart begins.

**A chart type may declare a role implied rather than bound** (Workstream A, the Outcome reframe, shipped 2026-07-30): a line's x is always the schema's one temporal field, and a bar's category is always its geographic level, so neither is offered as a dropdown. `lib/visualization/impliedRoles.js`'s `impliedBindings(chartTypeId, schema)` resolves both, strictly - a role the resolver cannot answer (an ambiguous temporal field, a schema with no geography) is omitted rather than guessed, and stays a real dropdown. The section renders the resolved role as a sentence instead - "Plotted against Year, set in Date Range", "One bar per location in Counties, set in Geographic Level" - naming the control that actually owns the setting, rather than as a disabled `Select` that would invite a click and explain nothing. Those two sections now render *below* Outcome rather than above it - the hint still names them by label, not by position.

Folding an axis out of the grid also folds the question the reader is answering: with the category or x-axis already decided by chart type and context, the remaining measure role reads as **Outcome** rather than Y-Axis - `roleLabel` returns it for any chart type that declares an implied role at all, whether or not this schema resolves one, so bring-your-own-data's line still reads "Outcome" even though its X-Axis stays a real dropdown (it has no temporal field to imply from). This is what used to be two controls asking the same question twice: the duplicate Category dropdown here and the Geographic Level select below it. Removing it did not add a mapping table - a bar's category was always `Location` (`Jurisdiction` on RHNA Progress, by label only), the same column Geographic Level already filters.

**Orientation is the one control this reframe keeps explicit.** Bar still offers a vertical/horizontal toggle here, beside the implied-role hint, because unlike category it is not inferable from anything already chosen elsewhere - a reader who wants a horizontal bar has to say so. A plain bar defaults vertical and a diverging one defaults horizontal (`appearance.diverging`, Workstream B - see *Bar absorbs Diverging Bar* under Appearance), so turning Diverging on never changes orientation on its own: silently moving a control the reader can already see is precisely the auto-binding behaviour the workbench withdrew.

**A Diverging bars switch sits beside orientation, for `bar` only** (Workstream B, shipped 2026-07-30): the retired `divergingBar` chart type is now `appearance.diverging` on a plain bar, writing `SET_APPEARANCE` / `diverging` and nothing else. Turning it on reveals Center reference and the rest of the dashboard-style controls in Appearance; turning it off hides them without touching orientation, the palette, or anything else the reader set.

> [!note] Implied is not auto-bound
> `withImpliedBindings` in `chartConfigStore.js` spreads the implied fields first and the reader's own bindings second, so an explicit choice - a saved view's `bindings.category`, a chart-type switch that carried a compatible field across - always wins. This looks like it violates *The reader binds every field*, but an implied role has exactly one valid answer, declared by the chart type, that the reader can see and change (by moving the Date Range slider or the Geographic Level select) - not a guess the editor made among several valid fields. `validateBindings` treats a resolved implied role the same way: never `MISSING_REQUIRED_ROLE`, because it was never unanswered. A chart type that declares a role implied but sits on a schema that cannot resolve it (checked via the resolved value, not the descriptor flag) still reports that role missing, because there it really is.

### Date Range

A single- or dual-handle slider bounded by `schema.yearRange`, writing `period.year` or `period.startYear`/`endYear`. Dual for the chart types whose period is a span (line, heatmap, Range) and for bar/choropleth when a change transform makes them two-period. Absent for modules with no time axis - RHNA Progress declares no `yearRange` for exactly this reason.

### Geographic Level

The section that absorbed the most. A level `Select` over `schema.subsets` writes `filters.subset` and keeps the source side effects that pairing demands: a level with a `subsetSource` forces that source, and `States` forces Census where the module has it. A choropleth is pinned to the level we hold geometry for rather than offered levels that would render blank.

Beneath it, a checkbox list of the individual places at that level - seven, then **Show more (N)**. Selection writes `filters.locations`; changing the level clears it, because a county name is not a region name and a stale filter would quietly match nothing.

Two controls sit above the list. A **search box** appears once the list is longer than the seven rows shown collapsed - five regions do not need a filter, five hundred cities are unusable without one. A **Select all** checkbox selects every row currently listed, and a **Clear (N)** button beside it drops the whole selection.

> [!note] "Select all" means "all of these matches"
> With a search active, Select all takes the filtered rows, not every location - a control sitting directly above a filtered list has to mean what the reader can see. **Clear** deliberately does the opposite and drops the entire selection, because a filtered clear would leave places selected that the reader cannot see to unselect. Reordering is also disabled while a search is active: an order written from the matches alone would silently drop every place the filter hid.

For chart types whose categories *are* places - line, bar, diverging bar - the same rows carry a drag handle and a visibility switch, writing `appearance.categoryOrder` and `appearance.hiddenCategories`, and the section also owns Top/Bottom N - behind **Advanced Mode**, the one block it hides. That is the point of folding them together: on a module, the things being ranked and the things being selected are the same list, and showing them as two lists of identical names was the confusion worth removing.

Every async state is named. Loading, "we could not load locations for this geographic level", and "no locations available for this geographic level" are three different sentences, because a failed request and an empty level are different problems.

> [!note] Empty means "let the ranking decide"
> `filters.locations: []` is not "no places". It means no explicit selection, so Top-N chooses. That is what lets a fresh chart draw something without the reader picking places one at a time, and it is why the key is omitted entirely from stored views when empty.

### Transform

Everything that changes what a measure says without changing which measure it is: how the values are expressed, and which slice of rows they are computed from.

Radio buttons over the bound measure's own `transforms` come first: Actual Value, Index to Base Year, Numeric Change, Percentage Change. A rate measure offers two options, not four - percent-of-a-percent is a category error, not a formatting choice, so a rate gets Percentage-Point Change instead.

Selecting Index to Base Year reveals a base-year `Select` bounded by `schema.yearRange`. It was a free number input before, which is how an out-of-range base year got in (flagged issue 4).

**Imported data gets the same section with two radios** - Absolute Values or Index to 100 at Base Period - added 2026-07-29. A pasted table has no field catalog to read `transforms` from, so the pair is fixed: the two-period change transforms are computed by the module fetch layer (`chartData.js`), which has no inline equivalent. The base periods are the imported x column's own values, ascending, not a module year range; the wording says "period" rather than "year" because a pasted time axis is as often months, quarters, or waves. Left unset, the `Select` reads "First period in the data", which is exactly what `transformRegistry.js`'s base-value fallback does.

The pair is offered only where index-to-100 actually lands: a `transformCapable` chart type whose inline shape carries a time axis (line, heatmap) and whose table holds more than one period. A bar chart tags every inline row with one implied period, so indexing would set every category to 100 - the section stays absent rather than offering a radio the renderer ignores. `inlinePeriods(table, spec)` in `lib/tabular/toSeries.js` answers "which periods does this shape actually plot", parsing them exactly as the shape builders do so an offered period always matches a `years` entry the transform sees.

`transformOptions(config, schema)` in `lib/visualization/transformRegistry.js` owns both lists - `{ transforms, basePeriods, inline }` - so the section, its registry gate, and the reducer read one answer. The reducer's half is `withExpressibleTransform`, which runs on every revalidation and drops an *imported-data* transform the chart can no longer express: switching an indexed line to a bar, or re-importing a table that now holds a single period. A module keeps its stranded transform and surfaces `TRANSFORM_NOT_ALLOWED` instead, because there the field catalog is the reader's own to fix and a silent rewrite would hide the notice explaining it.

`validateBaseYear` exempts inline mode for the same reason the periods come from the table: an inline chart plots every row it was given, so the year slider's window is not its domain, and comparing the two would warn about a mismatch that does not exist.

Beneath them sit the module's **stratification pins**, one `Select` per entry in `schema.filterDimensions`, each defaulting to the precomputed aggregate row ("All Ages", "Both Sexes", "Total") rather than to no filter. They lived under Datasets until July 2026, which read as a claim they never made: choosing renters aged 65+ does not change which dataset you are reading, it changes which rows the measure is computed over - the same kind of statement the radios above make. Housing Stress and RHNA Progress are where the mismatch was most visible, since a dataset toggle is the one thing neither module has ever had.

The section returns nothing at all for chart types whose descriptor is not `transformCapable` - scatter, pie, the Range family - rather than rendering an empty block (flagged issue 1).

`hasTransformControls(config, schema)` is the exported form of that decision and the Transform entry's only gate. It deliberately carries no `key`: "comparison" was wrong twice over. Nearly every chart type declares it, including the ones that cannot transform, so `key` alone kept the accordion header and hid only its contents; and the stratification pins have to survive on the chart types that declare no comparison at all, because a data table of stratified rows still needs to say which rows.

The predicate answers in two steps. A schema with `filterDimensions` always has something to show, whatever the chart. Failing that, the transform radios need a `transformCapable` chart type **and** either more than one transform from `transformOptions` or a `benchmark` role to label. A lone "Actual Value" radio reads as a broken control, so it is never drawn - which is what keeps the section absent on a single-transform measure, and on imported data that has no second period to index against. The benchmark half is module-only: "Difference from Benchmark" fetches a module series, and an imported table has none. The section re-checks `transformCapable` internally for the same reason it always has: stratification alone can open it, and a scatter plot should gain the pins without gaining radios it cannot honour.

> [!note] The header is the thing that disappears
> Returning `null` from a section component only empties the accordion body; the trigger, its label, and the brand rule still render. A section that can render nothing therefore has to say so through the registry, not just through its own return value.

### Labels, Appearance, Typography

**Labels** is five text inputs - Title, Subtitle, X-Axis Label, Y-Axis Label, Legend Title - each placeholdered with the label the chart would derive from its bindings. Blank means "keep the derived label", which is why the derived text is a placeholder and not a pre-filled value: a derived title keeps tracking the data when a binding changes, a typed one deliberately stops.

**Appearance** opens with the optional **Color** field binding for Line, Bar, Scatter, and Bubble, followed by the five shared controls in order: Color Palette, Legend Position, Horizontal Line Spacing (px), Vertical Line Spacing (px), Footnote. The moved dropdown still writes `bindings.color`; Appearance owns only its location, not a new appearance property. Everything below Footnote is chart-type-conditional - markers, the diverging-bar dashboard styling, the forest plot's interval and marker styles, the colour scale, the watermark, the tooltip template. A default line chart therefore shows Color plus the five shared controls, and a diverging bar grows the ones it needs. Orientation moved out to the Outcome section (Workstream A, 2026-07-30): it is the one degree of freedom bar/diverging bar still ask about explicitly, alongside the category or measure choice Outcome otherwise infers.

#### Bar absorbs Diverging Bar

Diverging Bar is not a chart type anymore (Workstream B, shipped 2026-07-30). It is `appearance.diverging` on a plain `bar` - a prop, not a component, the same way `pie` already varies through `hole`. The Center reference input and the dashboard-style controls (`DivergingStyleControls`: value-axis range, track rail, minimal axis, threshold colors) gate on `appearance.diverging` rather than on a chart type, so they appear the instant the reader flips the Diverging bars switch in Outcome and disappear the instant they flip it back - no chart-type switch, no lost bindings, no re-fetch.

`lib/visualization/toPlotly.js` routes on the same flag: a plain `bar` calls `barSpec`, a diverging one calls `divergingBarSpec`, and both draw from the identical `{category, value}` record contract `barSpec` and `divergingBarSpec` always shared - this was a router change, not a renderer change, and `toPlotly.catalog.test.js` asserts `{chartType: "bar", appearance: {diverging: true}}` renders byte-for-byte identically to the old `{chartType: "divergingBar"}` shape.

**The old id is retired, not deleted.** `lib/visualization/chartSpec.js`'s `RETIRED_CHART_TYPES` maps `divergingBar → bar`, and `normalizeSpec` rewrites a stored `divergingBar` view's `appearance` to `{ diverging: true, ...storedAppearance }` - the stored appearance spreads second, so `center`, `colorBuckets`, `valueRange`, `trackRail`, and `minimalAxis` all survive a migration untouched. `validateSpecShape` reports `CHART_TYPE_RETIRED` off the same map, so a re-saved bookmark quietly stops carrying the warning. The `divergingBar` descriptor itself stays registered in `chartRegistry.js` - marked `hidden: true` - for one release after the migration ships, so every code path that still reads `getChartType("divergingBar")` defensively keeps working; only `ChartTypeSection`'s tile grid and `ChartTypeStep`'s wizard gallery stop offering it, and `RHNA_PROGRESS_SCHEMA.supportedChartTypes` narrows to `["bar"]`. Deleting the descriptor outright, and the `case "divergingBar"` branches that read it directly in `toPlotly.js`, is the one deferred step - it needs a release to pass first, so a link saved the day before deletion still has something to resolve against.

**Typography** is six numeric fields - title, subtitle, axis label, legend, and data label sizes, plus decimal places. Each clamps to its own range on the way into the config rather than trusting the input's `min`/`max`, which browsers enforce only on form submission.

## The chart container

A single card: a centred, brand-underlined module title, a bordered body, and the action bar.

The body is the chart or the data behind it, chosen by a local `viewMode`. Chart mode is `PreviewPane`, with its full idle / unconfigured / loading / invalid / empty / error / ready vocabulary.

### Landing on a module builds nothing

A module page opens on a **skeleton** - a plot frame, axis ticks, and a row of placeholder bars under a prompt naming what to set - and issues **no data request at all**. The chart is built by the reader: the first change to any sidebar control arms the preview, and from then on it updates live on every change, chart-type switches included.

This is the `deferInitialRender` prop on `PreviewProvider`. The workbench opts in; the wizard leaves it off, because its Import step means the reader has already supplied data by the time a chart is on screen.

> [!note] Why the undo history is the arming signal
> "The reader changed something" is read from the store's `canUndo`, not from the request key. Undo history already excludes `COMPUTED_ACTIONS`, so the loader's own `SET_SERIES_COUNT` feedback cannot arm the chart and trigger the very fetch this defers. Keying off the request key instead would miss appearance-only changes, which do not alter the request. Arming is sticky: undoing back to the start leaves the chart rendered rather than blanking it.

Two cases opt back out, because in both the chart has already been asked for by name: an **iframe embed**, which has no sidebar to touch and would otherwise show a skeleton forever, and any **`?view=` deep link or saved view**, which names a specific chart. Both carry their own bindings, so both render immediately, exactly as before.

**The two views are the same height.** The body is free-height in chart mode, governed by its `min-h-130` floor; on the way into data mode its rendered height is measured and pinned inline, and the table is bounded by that box rather than allowed to grow. Without this the data view - 50 rows to a page - made the card taller, and because the workbench's grid row takes its height from this container alone, the sidebar beside it stretched too, so every toggle moved the whole page.

The height is measured rather than declared as a constant, because the chart view's own height depends on the chart type: PreviewPane's floor, or the taller of the plot, its border and its tab row. It is re-measured when the preview status changes, since a skeleton, a spinner and a rendered chart are not the same height. Where nothing can be measured the CSS floor stands in.

**Data mode shows the entire cleaned dataset** - every row and every column of the module's CSV, via `?view=table&full=1`, not the narrowed table the chart draws. A reader who switches to the data is asking what is in the file; the chart's own columns are already visible as the chart. It is fetched lazily on first open and cached for the session, and the hook lives in `ChartContainer` rather than in the table so the load survives toggling back to the chart. Loading, error, and empty are named states, like everywhere else data is fetched.

`ChartContainerFooter` carries the View Chart | View Data toggle and the two export dropdowns. It takes preview state as props rather than calling `usePreview()`, which keeps it a presentational bar that can mount anywhere.

Both dropdowns are told whether the preview is `ready`, and they act on it differently:

| | Not ready |
|---|---|
| **Export Chart** | Disabled outright. Image export runs off the mounted graph div, and there is no figure. |
| **Export Data** | Open. Its **Original data (entire cleaned dataset)** items are addressed by `?view=table&full=1` from config and schema alone, so they never needed a rendered chart; only the **Chart data (as displayed)** items grey out. |

That distinction matters more now that a module opens unarmed: the dataset is the thing a researcher most often wants, and making them build a chart first to get a CSV they were not going to look at is a toll. The trigger closes only when neither source has anything to write.

`ExportMenu.js` exports `ExportChartButton` and `ExportDataButton` separately for this reason; its default export composes both with the image-quality control for the wizard's Export step. Export Data keeps both sources: the displayed table, and the entire cleaned dataset fetched via `?view=table&full=1`.

### The reader binds every field

Arming the preview is not the same as having a chart to draw. The workbench passes `autoBind={false}` to `ChartConfigProvider`, and that one flag is the whole manual-encoding rule:

| Where | With `autoBind` (the wizard) | Without it (the workbench) |
|---|---|---|
| Opening the editor | The default preset seeds a chart type and its bindings. | Chart type only; `bindings` holds nothing **except an implied role the chart type resolves** - a line opens with `x: "Year"` already set, from the schema alone, not from the preset. |
| `SET_CHART_TYPE` | `bindingsForPreset` carries compatible bindings **and** fills the rest from the preset defaults and the field catalog. | `carriedBindings` carries the compatible ones and stops. Roles the new type does not declare fall away; roles it needs and did not inherit stay unset - **unless the new type implies one**, in which case `withImpliedBindings` resolves it regardless of `autoBind`. |
| A required role left unset | An error, reported in the sidebar and blocking the preview. | Neither. The preview reports `unconfigured` and draws the skeleton. An implied-and-resolved role is never in this row at all - it was never unset. |

The skeleton names the gap rather than only reporting one: `unsetRoles` reads the roles out of the validation findings, so the caption reads "Set X-Axis and Y-Axis to build this chart" for a scatter (neither axis implied) or "Set Outcome to build this chart" for a line or bar (the one role Workstream A still asks for), falling back to the generic prompt when no finding carries a role.

> [!note] Unfinished is not invalid
> `MISSING_REQUIRED_ROLE` and `MISSING_PRESET_ROLE` are still error-level findings - a chart with no Y-axis cannot be drawn, exported, or saved as a view, and `hasBlockingErrors` is unchanged, so `savedViews.js` still refuses one. What changed is who treats them as a fault. `validation.js` names them in `INCOMPLETE_CODES`, and the two surfaces that speak to the reader - `ValidationNotice` and `PreviewPane` - suppress them where nothing is auto-bound. Every other error, including one the reader can actually cause (a source not chosen, a level a choropleth cannot draw), reports exactly as before.

Two consequences are worth stating plainly. **No request goes out for a half-set chart**: `isUnconfigured` short-circuits the load effect, so a chart-type switch that leaves a role empty costs nothing and cannot surface a server error for a question the reader never asked. And **the skeleton wins the frame**: the unconfigured verdict is computed ahead of any preview state the load effect has yet to overwrite, so clearing a binding shows the skeleton on the same commit rather than flashing the previous chart until the effect catches up.

Bring-your-own-data is deliberately outside all of this. It auto-maps pasted columns onto roles by name and type, `inlineRenderBlock` already explains an unmappable table in its own words, and an unset role there is a dead end rather than a step not yet taken.

## The data views

`chartData.js` is the only place the browser talks to a module API. It maps chart type to a query "view" - the server never sees "chart type", only a data-shape verb - and builds the query string.

| View | Shape | Used by |
|---|---|---|
| `line` | `{ series: [{ location, years[], values[] }] }` | line |
| `category` | `{ period, records: [{ location, category, value }] }` | bar, diverging bar, pie |
| `twoPeriod` | `{ startYear, endYear, records: [{ category, start, end }] }` | Range, forest |
| `pairs` | `{ period, records: [{ location, x, y, size? }] }` | scatter, bubble |
| `matrix` | `{ matrix: { x, y, z } }` | heatmap, dot plot |
| `geo` | category values joined to GeoJSON `GEOID` | choropleth, symbol map |
| `table` | every column of the cleaned CSV | data table, dataset export |
| `locations` | `{ locations: string[], subset: string }` | the geographic multi-select |

### `view=locations`

Added by this work. Every module route accepts `?view=locations&subset=<subset>` and answers with exactly `{ locations: string[], subset: string }` - nothing else, because the multi-select needs nothing else. It resolves **before** each route's measure and period validation, since it carries neither.

Each module resolves its own subset rows first and hands them to the shared `buildLocationList`, which does no level filtering of its own. That matters because the resolution differs per module: Building Permits aggregates metros into regions and invents a "Rest of US" row, and RHNA Progress reads `Jurisdiction` rather than `Location`.

`useLocationOptions(schema, filters)` consumes it, cached per module + subset in a module-level `Map` so re-opening a level never re-fetches, and aborting in flight so dragging through levels cannot let a slow earlier response overwrite a newer list.

## Testing

Tests live under `tests/js/`, mirroring the source path, and run under Vitest with `@testing-library/react`. Three conventions apply.

**Assert on behavior, not markup.** Query by role, label, and accessible name. The one deliberate exception is `ModuleSidebar.layout.test.js`, which asserts CSS classes because the positioning *is* the behavior and jsdom cannot lay out.

**Every async boundary gets three tests** - loading, error, and success. `useLocationOptions` and the location picker are the main new boundaries.

**Migration tests are not optional.** Each of the three config-shape changes above round-trips an old stored view. A user with a bookmarked link is the regression these catch.

Two architecture tests keep the removals honest: `architecture/moduleWorkbench.removals.test.js` fails if any file under `app/`, `components/`, or `lib/` imports the settings-tier gate or the codebridge, and `ModuleSidebar.composition.test.js` fails if a wizard-only control is wired into the module rail.

The manual-encoding rule is tested at each of its three layers, and each layer also asserts the auto-binding surface is untouched. `chartConfigStore.test.js` covers the store (opens with its implied roles resolved and nothing else, honours a view's bindings and lets one override an implied role, carries only what the new chart type accepts on a switch while still resolving what it implies); `wizard/PreviewContext.unconfigured.test.js` runs the real store against the real `pophousing` schema and asserts that an unset role fetches nothing, that setting the last one renders, and that a bar reached from a line renders on its implied category rather than returning to `unconfigured`; `wizard/PreviewPane.skeleton.test.js` and `ValidationNotice.test.js` cover what the reader sees, including that an unset role produces no alert. `impliedRoles.test.js` and `chartRegistry.catalog.test.js` cover the resolver itself: every module schema resolves a temporal field for line and `Location` for bar, bring-your-own-data resolves neither, and an ambiguous or missing candidate is omitted rather than guessed.

## Settled since the split

**Should a chart-type switch keep drawing a chart?** No - settled 2026-07-29. Switching chart types re-seeded every unfilled role from the preset defaults, so a reader clicking through the tiles was shown a succession of charts nobody had asked for, and the roles that could not be seeded were reported as configuration errors instead. The workbench now binds nothing on the reader's behalf and shows the skeleton until each encoding is set. See *The reader binds every field*.

**Does the location multi-select need search?** Yes - added 2026-07-28, along with Select all / Clear. Seven-plus-Show-more was fine for nine regions and workable for fifty-eight counties, but not for the roughly five hundred cities Population & Housing carries. See *Geographic Level*.

**Should the Axis section ask for a role the chart type has already decided?** No - settled 2026-07-30 (Workstream A, the Outcome reframe). A line's x is always the schema's one temporal field and a bar's category is always its geographic level, so asking for both was one question asked twice - once here, once in Geographic Level - and the duplicate Category dropdown was a symptom of the same mistake, not a separate one. The section is renamed **Outcome**, a chart type may declare a role `impliedRoles` in the registry, and `lib/visualization/impliedRoles.js` resolves it from the schema rather than from a dropdown. See *Outcome*.

Three questions the plan left open for Workstream A were settled during the build, following the plan's own proposed defaults:

- **Does Outcome apply beyond line and bar?** No. `impliedRoles` is declared only on `line` and `bar` (`divergingBar` inherited the same entry before it retired - see below); scatter, bubble, heatmap, forest, and the Range family keep their full grid and gain nothing but whatever relabelling `roleLabel`'s descriptor-level check does not touch.
- **What is a bar's category on a module with no geography?** It falls back to a real dropdown, the same fallback bring-your-own-data uses. `impliedBindings` omits rather than guesses, and `validateBindings` checks the resolved value rather than the descriptor flag, so a schema with no geography field reports the role missing exactly as it would have before Workstream A - no schema-time error, no special case.
- **Should the wizard get the reframe at all?** Yes, unconditionally - there is no wizard-specific code. `OutcomeSection` reads the same registry-level `impliedRoles`; bring-your-own-data's schema resolves neither role (no temporal field, no geography field), so its X-Axis dropdown stays exactly as it was, and only the Y role's label changes to "Outcome" (a chart-type-level fact, not a per-schema one).

**Does Bar absorbing Diverging Bar change what a diverging chart looks like?** No - settled 2026-07-30 (Workstream B). `appearance.diverging` on `bar` routes through the exact same `divergingBarSpec` renderer the `divergingBar` chart type always called, so nothing about how a diverging bar draws changed - only how a reader turns one on (a switch in Outcome, beside orientation, instead of a separate tile) and what the stored config calls it (`{chartType: "bar", appearance: {diverging: true, ...}}` instead of `{chartType: "divergingBar"}`). A stored `divergingBar` view migrates automatically, with its center reference and dashboard styling intact, and a `CHART_TYPE_RETIRED` warning names what changed. See *Bar absorbs Diverging Bar*.

**Where should Outcome sit relative to Date Range and Geographic Level?** Directly after Chart Type - moved 2026-07-30, an audit follow-up rather than a workstream phase. Workstream A's plan and its Phase 3 both put Outcome after Geographic Level (the order the old Axis section already had), but Outcome's content is entirely about what the chart type does and does not ask for, so it now reads immediately beside the Chart Type tiles rather than after two sections it only references by name. Only `sidebarSections.js`'s registry order changed - the section's gate, component, and every behavior described under *Outcome* are unchanged, and the `value: "axis"` key any `only`/`exclude` caller keys on did not move either.

## Workstream A - The Outcome reframe

> [!success] Built and audited 2026-07-30
> All five phases below landed as written: `AxisSection.js` is `OutcomeSection.js`, `impliedRoles.js` exists, the store and validator resolve implied bindings everywhere, and the docs below (*The idea in one sentence* onward) describe the shipped behavior. The as-built *Outcome* section under *The sidebar sections* above is the current source of truth for what the reader sees; this plan section is kept for the phase-by-phase reasoning and the file/line map. The audit confirmed all four of A's per-workstream questions and found none of the three A-class known-wrong implementations; findings A-i and A-ii under *Audit results, 2026-07-30* are missing regression guards, not defects.

Feedback item 2 asks for the duplicate Category dropdown to be removed and wired to Geographic Level. The Settings Reframing callout asks for the Axis grid to become a single Outcome dropdown, with the other axis inferred from the chart type. These are one change: the reason Category is duplicated is that the Axis grid asks the reader to bind a role the chart type has already decided.

### What is true today

`AxisSection.js` renders one `Select` per role returned by `rolesFor(config)`, which is the chart-type descriptor's `requiredRoles` plus `optionalRoles`, minus `hiddenRoles`, plus `group`. Two of those dropdowns are not real choices. A line's `x` is constrained to `[TEMPORAL]`, and a module carries one temporal field, so the dropdown offers one option. A bar's `category` is constrained to `[DIMENSION]` and every preset defaults it to `Location`, which is the same column the Geographic Level select is already filtering. `GeographySection.js` says as much in code: `PLACE_CATEGORY_CHART_TYPES` already asserts that for line, bar, and diverging bar the categories *are* the places.

### The idea in one sentence

A chart type may declare that a role is **implied** rather than bound, and an implied role is resolved from the schema and the reader's existing geography or period choices instead of being asked for.

### Phase 1 - Declare implied roles, change nothing visible

**New file: `lib/visualization/impliedRoles.js`.** Client-safe, no `node:fs`, matching `chartRegistry.js`'s constraint.

```js
/** The field a chart type implies for a role, or {} when nothing resolves. */
export function impliedBindings(chartTypeId, schema) { /* … */ }

/** Does this chart type declare this role as implied? Descriptor-only. */
export function isImpliedRole(chartTypeId, role) { /* … */ }

/** The sentence the sidebar prints in place of the missing dropdown. */
export function impliedRoleHint(role, config, schema) { /* … */ }
```

`impliedBindings` takes a **chart type id, not a config**. That is deliberate: `validateBindings(chartTypeId, bindings, schema)` in `validation.js:32` has no config to pass, and giving the resolver a signature it cannot call would force a second, divergent copy of the same logic.

Two resolver sources, both strict:

| Source | Resolution | Falls back to |
|---|---|---|
| `"temporal"` | `schema.temporalField` when it names a field of kind `temporal`; otherwise the sole field whose `kind` is `temporal` | Omits the role entirely when zero or more than one candidate exists |
| `"geography"` | `schema.geographyField ?? "Location"`, when that key exists in `schema.fields` and its kind satisfies the role's `roleConstraints` | Omits the role entirely |

Omitting rather than guessing is the contract. A role the resolver cannot answer stays a dropdown and stays validated, which is what makes bring-your-own-data (Phase 4) work with no special case and what protects a future module that has no geography.

**Registry additions in `lib/visualization/chartRegistry.js`**, alongside the existing `requiredRoles` on each descriptor:

```js
line:         { …, impliedRoles: { x: "temporal" } },
bar:          { …, impliedRoles: { category: "geography" } },
divergingBar: { …, impliedRoles: { category: "geography" } },  // omit if B4 has landed
```

No other descriptor gains the key. `heatmap` also declares `x: [TEMPORAL, DIMENSION]`, and it is deliberately left alone: its x is a real choice between two kinds.

`impliedRoleHint` reads the field's `label` and the current `filters.subset` to produce "Plotted against Year, set in Date Range" and "One bar per jurisdiction in Counties, set in Geographic Level". Note that RHNA Progress's `Location` field carries `label: "Jurisdiction"`, so reading the label rather than the key is what makes that sentence correct for free.

**Tests.**

| File | Test | Asserts |
|---|---|---|
| `tests/js/lib/visualization/impliedRoles.test.js` (new) | resolves the temporal field on every module schema | iterating `MODULE_SCHEMAS`, `impliedBindings("line", schema).x` is truthy and names a `temporal` field |
| | resolves `Location` on every module schema | `impliedBindings("bar", schema).category === "Location"` |

### Phase 2 - Make the implied binding real everywhere config is read

**`components/chart-builder/chartConfigStore.js`.** Add one helper beside `carriedBindings` (around line 227):

```js
/** Implied roles filled in, without disturbing anything the reader chose. */
function withImpliedBindings(bindings, chartTypeId, schema) {
  return { ...impliedBindings(chartTypeId, schema), ...bindings };
}
```

Implied values spread **first**, so an explicit binding always wins. Apply it at three call sites, and only these three:

| `lib/data/geography.js` | Export the coordinate source - either `loadCentroids(level)` deriving from the polygons, or a loader for the new point file. Cache it the way `loadGeometry` (line 67) is cached, and reuse `getFeatureIdLookup(level)` (line 94) for the name-to-id half rather than writing a second lookup |
| `app/api/geography/route.js` | Accept the coordinate request, or add a sibling route. Keep the existing `Cache-Control` treatment: coordinates are as static as polygons |
| `components/chart-builder/chartData.js:828-831` | Extend the `geometryPromise` ternary so `symbolMap` fetches coordinates the way `choroplethMap` fetches polygons, keyed by the same `geometryLevelForSubset(config.filters.subset)` |
| `lib/visualization/toPlotly.js:1708-1743` | `symbolMapSpec` joins each record to its coordinate by `GEOID`, using the `FEATURE_ID_KEYS` mapping the choropleth uses, and reads `lat`/`lon` off the join rather than off the record |

> [!note] A symbol map inherits the choropleth's county-only limit
> `AVAILABLE_GEO_LEVELS` is `["counties"]` (`lib/data/geography.js:38`), so a symbol map can only draw the level we hold geometry for. `GeographySection` already pins a choropleth to Counties for exactly this reason (line 80-83); the symbol map needs the same pin, or it will offer levels that render blank.

The join is the one place a symbol map differs structurally from a choropleth. A choropleth hands the whole FeatureCollection to Plotly with `featureidkey` and lets Plotly match (`toPlotly.js:1650-1653`), so a name mismatch is only ever reported by the server's own `unmatched` array. A symbol map has to resolve coordinates itself, which means it can drop a record client-side. Those records must feed the same `geoUnmatched` path the store already carries through `SET_SERIES_COUNT`, not silently shrink the trace. The load gets the three named states - loading, error, empty - that every other async boundary in this codebase has.

**Tests.** `tests/js/components/chart-builder/chartData.test.js`: a `symbolMap` config fetches coordinates and a `line` config does not. `tests/js/lib/visualization/toPlotly.test.js`: a symbol map with two joinable records produces two finite `lat`/`lon` pairs, and one unjoinable record lands in `unmatched` instead of the trace.

### Phase 4 - Guard, and guard the class of bug

Until Phase 3 lands, `symbolMap` should not be reachable: remove `"symbolMap"` from `TILE_ORDER` in `ChartTypeSection.js:37`. Note that `orderedChartTypes` (line 48) deliberately appends any registered id the list forgot, so removing the tile is not enough on its own - either give the descriptor an `unreachable: true` marker that `orderedChartTypes` filters, or narrow every module's `supportedChartTypes`. The first is less to undo later.

Then add an architecture test in `tests/js/architecture/`, alongside the two that already keep the removals honest: **a chart type declaring `requiresGeometry` must have a geometry loader wired for it in `chartData.js`**. `choroplethMap` passes today, `symbolMap` fails today, and the next map type cannot repeat this silently.

**Done when.** No module offers a Symbol Map tile, and the new architecture test fails if someone re-adds one without a loader.

## Audit protocol

Each phase above is written to be implemented in one commit and then audited independently. The auditor's job is not to re-derive the design; it is to check that what was built matches what was specified, and to look for the specific ways this plan can be implemented plausibly but wrongly.

### Commands

```text
npm run build                                    # must succeed
npx vitest run                                   # full suite
npx vitest run tests/js/docs                     # the documentation contract
npx vitest run tests/js/architecture             # the removal and wiring guards
git diff --stat main...HEAD                      # scope: does the diff match the phase?
```

A phase whose diff touches files its **Files touched** table does not name is either mis-scoped or found something the plan missed. Both are worth a comment; only the second is worth accepting.

### Invariants that must hold after every phase

These are properties of the whole editor, not of any one workstream, and each has a test that already exists or is added by a phase above.

| Invariant | How to check |
|---|---|
| A bookmarked `?view=` link still opens the chart it named | The migration tests in `moduleWorkbenchMigrations.test.js` and `chartSpec.test.js` |
| The workbench never binds a field the reader could have chosen differently | `chartConfigStore.test.js`'s carried-bindings tests, unchanged |
| An unfinished chart shows a skeleton, not an error | `PreviewPane.skeleton.test.js` and `ValidationNotice.test.js` |
| No request goes out for a half-set chart | `wizard/PreviewContext.unconfigured.test.js` |
| The standalone tool keeps presets, saved views, multi-chart, layers, and the activity log | `ModuleSidebar.composition.test.js` and `VisualizationWizard.overhaul.test.js` |
| The two container views stay the same height | `ChartContainer.test.js` |
| This document does not describe controls that no longer exist | `tests/js/docs/moduleWorkbenchDocs.test.js`, plus reading |

### Known-wrong implementations to look for

Each of these passes a naive test and is wrong. They are the failure modes this plan is written to prevent, listed so an auditor can check for them directly.

| Workstream | The plausible mistake | How it shows up |
|---|---|---|
| A2 | Implied bindings applied **after** a stored view's `initial.bindings` merge | A deep link that overrides `category` silently reverts to `Location`. Check the spread order at `createChartConfig` |
| A2 | Seeding folded into `carriedBindings` | The chart-type-switch test still passes, but the function no longer means what its name and docstring say. Check the call sites, not just the behaviour |
| A2 | Validation skipping a role via `isImpliedRole` instead of `implied[role]` | A schema that cannot resolve the role stops reporting it missing, and the chart fails at the data layer instead of in the sidebar |
| A3 | The implied hint rendered as a disabled `<Select>` | `getAllByRole("combobox")` still finds it. The hint must not be a form control |
| A3 | `roleLabel` changed only inside the section | The skeleton caption and validation notice still say "Y-Axis". Both import the same function; check all three render sites |
| B1 | `divergingBarSpec` edited to accept a flag | The router is the change; the two renderers stay untouched. A diff into either is a signal |
| B3 | The `diverging: true` rewrite placed in `migrateSpec` | Passes on a v1 fixture, runs for no real stored view, because `migrateSpec` returns early at `SPEC_VERSION`. Must be in `normalizeSpec` |
| B3 | Stored appearance spread before the flag | `center`, `colorBuckets`, and `valueRange` are lost, and the migrated chart changes meaning without failing |
| B3 | `PRESET_ORDER` reordered | Every new bar chart silently becomes diverging, because `presetForChartType` returns the first match |
| C2 | The skeleton's `aria-label` or height floor changed alongside the shape | The container's measured height moves and the sidebar beside it stretches on every toggle |
| D3 | Unjoinable records left as `undefined` coordinates | Plotly renders fewer points than the data has, with no `unmatched` report. The join must feed the existing array |
| D4 | The tile removed from `TILE_ORDER` only | `orderedChartTypes` appends any registered-but-unlisted id, so the tile comes back |

### Per-workstream audit questions

**A.** Does `impliedBindings` take a chart type id rather than a config, and does `validateBindings` actually call it? Does every module still open with no error reported? Does a bar chart drawn before the change and after produce the same figure? Does `grep -rn "AxisSection"` return only the tombstone?

**B.** Are `barSpec` and `divergingBarSpec` byte-identical to their pre-change selves? Does the equivalence test in `toPlotly.catalog.test.js` compare full `toPlotly` output rather than one trace field? Does a stored `divergingBar` view with a `center` of 1 and the dashboard bucket list open unchanged?

**C.** Does every one of the thirteen chart types have a declared shape? Does `ChartContainer.test.js` pass without modification?

**D.** Was the diagnosis reproduced and recorded before any fix was written? Does the new architecture test fail when `symbolMap` is re-added without a loader - checked by actually re-adding it, not by reading the test?

### What an auditor should reject

A phase that changes behaviour the plan did not ask it to change, even improvingly. A test that asserts an implementation detail rather than a behaviour, against the *Assert on behavior, not markup* convention. A migration without a round-trip test. A section that grows a control the mockup did not name. And any commit that leaves the suite red on the argument that a later phase fixes it - the phases are ordered so that none of them need to.

### Audit results, 2026-07-30

Workstreams A (Phases 1-5) and B (Phases 1-3) were audited against the protocol above on 2026-07-30. `npm run build` succeeds and the full Vitest suite is green at 694 tests across 79 files.

**Every known-wrong implementation was checked against the diff and none is present.**

| Checked | Verdict |
|---|---|
| A2 - implied bindings applied after the stored-view merge | Correct. `withImpliedBindings` wraps `base.bindings` in `createChartConfig`, and `initial.bindings` still merges over it afterwards, so a deep link naming its own `category` keeps it |
| A2 - seeding folded into `carriedBindings` | Correct. `carriedBindings` is untouched; `withImpliedBindings` is a separate helper applied at exactly the three named call sites |
| A2 - validation skipping via `isImpliedRole` | Correct. `validateBindings` guards on `implied[role]`, and a test proves a schema with no `Location` still reports `category` missing |
| A3 - the hint rendered as a disabled `Select` | Correct. It is a `<p className="text-sm text-muted-foreground">`, though nothing asserts that - see finding A-i |
| A3 - `roleLabel` changed only inside the section | Correct. `roleLabel` stays exported from the renamed file and both external importers (`PreviewPane.js`, `ValidationNotice.js`) were repointed |
| B1 - a renderer edited to accept the flag | Correct. `barSpec` and `divergingBarSpec` are byte-identical to their pre-change selves; `toPlotly.js`'s only edits are `measureAxes`, one comment in `linePositionCounts`, and the adapter switch |
| B3 - the rewrite placed in `migrateSpec` | Correct. It is in `normalizeSpec`, beside the existing `RETIRED_CHART_TYPES` lookup |
| B3 - stored appearance spread before the flag | Correct. `{ diverging: true, ...(migrated.appearance || {}) }`, with round-trip tests for `center`, `valueRange`, `trackRail`, `minimalAxis`, and `colorBuckets` |
| B3 - `PRESET_ORDER` reordered | Correct. The list is unchanged and `compare-places` still sits at index 1, ahead of both diverging presets |
| D4-class - the tile removed from `TILE_ORDER` only | Avoided. `divergingBar` gained `hidden: true` and `orderedChartTypes` filters on it, with a test asserting no stray Diverging Bar tile appears |

The per-workstream questions all answer as the plan intended. `impliedBindings` takes a chart-type id; `validateBindings` calls it; `grep -rn "AxisSection"` returns only the `EncodingSection.js` tombstone (updated to name `OutcomeSection.js`); the `toPlotly` equivalence test compares whole figures with `toEqual`, not one trace field; and a stored `divergingBar` view carrying `center: 1` plus the dashboard bucket list opens unchanged.

Four findings came out of the pass. None changes what a reader sees.

**A-i - the hint's "not a form control" guard is missing.** Phase 3's test table asks that the implied-role hint be asserted unreachable through `getByRole("combobox")`, precisely because the plausible wrong build is a disabled `Select`. `OutcomeSection.test.js` asserts the sentence's text and the dropdown's absence, but never that the sentence is not itself a control. The code is right today and nothing would go red if someone changed it.

**A-ii - the registry's implied-kind assertion restates the resolver instead of exercising it.** `chartRegistry.catalog.test.js` computes `const resolvedKind = source === "temporal" ? "temporal" : "dimension"` and checks that against `roleConstraints`, which is the resolver's own mapping written out a second time rather than a resolved field's actual `kind`. It cannot fail if a resolver starts returning something else. This is the *implementation detail rather than behaviour* case the protocol says to reject; coverage is not zero, because `impliedRoles.test.js` does resolve against every entry in `MODULE_SCHEMAS`, but that assertion is where the guard was supposed to live.

**B-i - `deriveLabels.js` needed the flag and no phase table names it.** `axisBindingNames` chose its category/measure axis mapping from `chartType === "divergingBar"`, so a `bar` with `diverging` on would have derived its axis titles the plain-bar way. The implementer extended it to read the flag and added `tests/js/lib/visualization/deriveLabels.test.js`. This is the accept-and-record case: the plan missed a fourth read site, and Phase 1's file table should name `lib/visualization/deriveLabels.js` alongside `toPlotly.js`.

**B-ii - Phase 4's deletion list is incomplete.** Five more sites still branch on the retired id and are not in Phase 3's *Other call sites* table: `QUERY_SHAPES` in both `components/chart-builder/chartData.js` and `lib/tabular/toSeries.js`, `GROUP_SECTIONING_RECORD_CHARTS`, and two chart-type comparisons in `chartData.js` (the change-transform loader and the series-name reader). All five list `bar` and `divergingBar` together and treat them identically, so nothing is broken now - a diverging bar is a `bar` and takes the `bar` branch. They are dead weight to remove with the descriptor, not a defect.

Two smaller notes, recorded rather than filed:

- `PreviewPane.skeleton.test.js` now expects "Set X-Axis and Outcome to build this chart." for a line, a caption no real module can produce, since a line's `x` resolves on every module schema and is never reported missing. The test hand-builds its findings, so it passes; it just no longer describes a reachable state. The reachable captions are the ones the *Outcome* section above names.
- `OutcomeSection`'s orientation control falls back to `diverging ? "horizontal" : "vertical"` when `appearance.orientation` is unset, which would read as the switch moving orientation - the one thing Phase 2's callout forbids. It is unreachable: both `createChartConfig` and `SET_CHART_TYPE` seed `appearance` from `bar.defaults`, which pins `orientation: "vertical"`. Were it ever reached, the displayed value would still match what `divergingBarSpec` draws, which defaults horizontal on anything but an explicit `"vertical"`.

> [!note] The working tree bundles a third change
> The diff audited here also carries Advanced Mode (`components/chart-builder/advancedMode.js` plus its wiring in `CategoriesSection`, `GeographySection`, `ModuleSidebar`, and `EditStep`), which belongs to neither workstream. It is documented as as-built under *Advanced Mode* above, so nothing is undocumented - but `git diff --stat` cannot be used to scope-check A or B against their **Files touched** tables until the three changes land as separate commits.

## Open questions

**Does turning on Diverging change orientation?** The proposal is no: the reader owns orientation after Workstream A, and `divergingBar`'s horizontal default becomes a preset concern rather than a switch side effect. The alternative is that a diverging bar looks wrong on first click and the reader has to fix it.

**Centroids or a point file for the symbol map?** Phase D2. This is the only item here that could turn into pipeline work rather than editor work.
