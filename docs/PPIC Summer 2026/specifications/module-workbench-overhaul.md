# Module Visualization Tool Overhaul - Implementation Plan

> [!info] Who this document is for and how to read it
> This is a **plan, not an as-built guide**. Nothing described here is shipped. It is written for the programmer (or agent) who will execute the work, and it assumes familiarity with [[graphEditor-overhaul]] and [[projectSpec]]. Read *Scope and Signed-off Decisions* first - it records what was decided in the kickoff conversation and is the contract the rest of the document is built on. Then read *Target Architecture* for the shape of the result, the *Sidebar Specification* for what each control must do, and finally the *Phases*, which are the actual work order. Each phase ends with its own unit test table; the tests are part of the phase, not a follow-up.

> [!warning] This overhaul splits one editor into two divergent surfaces
> Today `/[module]` and `/visualization-tool` are the *same* component (`VisualizationWizard`) with a different `steps` prop. After this work they are two different products: modules get a single-screen workbench with a curated control set, and the standalone tool keeps the full-power wizard. Every shared component touched below must be checked against **both** surfaces before a phase is called done.

## Scope and Signed-off Decisions

These were settled before planning began. They are not open for re-litigation inside a phase; if a phase surfaces a reason to revisit one, stop and raise it rather than deviating.

| # | Question | Decision |
|---|---|---|
| 1 | What happens to the four-step wizard? | **Replace it on modules, keep it for `/visualization-tool`.** Module pages become a single screen; the standalone tool keeps Import → Chart Type → Edit → Export. |
| 2 | Where do `series` and `color` encoding bindings go? | **Into the Axis section.** Axis becomes a four-control grid: X-Axis, Y-Axis, Series, Color. |
| 3 | What happens to category ordering? | **Rolled into Geographic Level** for chart types whose categories *are* places. For every other chart type it renders as its own disclosure dropdown. |
| 4 | Group binding, tab-by-column, Top-N? | **Kept** in the module sidebar. |
| 5 | What is dropped outright? | **Slopegraph** (`slope` chart type), the **code editor** (GUI ⇄ Code toggle and the R/Stata panel), and the **Basic/Moderate/Advanced settings-tier switch**. |
| 6 | What is unwired from modules but kept in the standalone tool? | Presets, saved views, the multi-chart workspace toolbar, the editor activity log, and config import/export. |
| 7 | Range chart (`dumbbell`)? | **Kept.** Only Slopegraph is dropped. The mockup's twelve-tile grid is illustrative, not an exact allowlist. |
| 8 | Datasets checkbox behavior? | **Checkboxes rendered, one-at-a-time selection.** Maps onto the existing single `filters.source` with no data-layer change. Section hides entirely when a module has fewer than two datasets. |
| 9 | Where does the geographic multi-select get its options? | **A new `view=locations` API view**, shared across module routes, returning the distinct `Location` values for a subset. |
| 10 | Standalone tool sidebar? | Follows the same section composition as the module sidebar, **excluding Chart Type** (which remains its own wizard step there). |

## Current State

### What exists today

The per-module route `/[module]` renders `ModuleEditor`, a thin wrapper over `VisualizationWizard` with `MODULE_STEPS = ["viewData", "chartType", "edit", "export"]`. The wizard renders a header card with `StepNav` and `MultiChartToolbar`, then one step at a time. Every step uses `StepShell`, a two-column layout with a resizable controls card on the left and a preview card on the right.

The control sections themselves live in `ChartSidebar.js`, which exports `TOP_SECTIONS`, `visibleSectionsFor()`, and `SidebarSections({ only })`. The Edit step calls `SidebarSections` with `only = ["data-sources", "date-range", "encodings", "comparison", "labels", "appearance"]`. `ChartSidebar`'s own default export - the resizable, `position: fixed` Radix sidebar with a two-phase zoom resize handle - is **not currently mounted anywhere**; only its named exports are used. That dead shell is a cleanup opportunity, not a foundation.

State lives in `chartConfigStore.js`: a `useReducer` over a *workspace* (up to four charts plus a layout) wrapped in undo/redo history, exposed through `useChartConfig()` as `{ config, dispatch, schema, workspace, canUndo, canRedo }`. Data loading is `chartData.js` → the module API route selected by `schema.apiPath`. `PreviewContext` holds the loaded result, status, and the mounted Plotly graph div.

## Target Architecture

### Two surfaces, one config store

```text
app/[module]/page.js
└── ModuleWorkbench                       (new - replaces ModuleEditor)
    └── ChartConfigProvider / PreviewProvider
        ├── ModuleSidebar                 (new - the mockup's left rail)
        │   └── ModuleSidebarSections     (new - composition of section components)
        └── ChartContainer                (new - the mockup's right card)
            ├── ChartContainerTitle
            ├── ChartCanvas               (PreviewPane, chart mode)
            ├── ChartDataTable            (DataTableView, data mode)
            └── ChartContainerFooter      (View Chart | View Data, Export Chart | Export Data)

app/visualization-tool/page.js
└── VisualizationWizard                   (kept, DEFAULT_STEPS)
    └── EditStep → ModuleSidebarSections without the chart-type section
```

The two surfaces share `ChartConfigProvider`, `PreviewProvider`, `chartData.js`, `toPlotly`, and every section component. They differ only in the **shell** (workbench vs wizard) and in the **section list** each shell composes.

### The section-composition contract

`ChartSidebar.js`'s `TOP_SECTIONS` array plus `visibleSectionsFor()` is the right idea and should survive, but the array itself is re-authored. Today a section is gated by chart type (`section.key` against `chart.sidebarSections`) and by settings tier (`isVisible(section.controlId, config.tier)`). With tiers dropped, gating collapses to two predicates: does this chart type use the section, and does this module's schema supply the data the section needs. That gives a cleaner signature:

```js
// lib/visualization/sidebarSections.js  (new - moved out of ChartSidebar.js)
export const SIDEBAR_SECTIONS = [
  { value: "datasets",   label: "Datasets",         Component: DatasetsSection,   when: hasMultipleDatasets },
  { value: "chart-type", label: "Chart Type",       Component: ChartTypeSection },
  { value: "date-range", label: "Date Range",       Component: DateRangeSection,  when: hasTemporalData },
  { value: "geography",  label: "Geographic Level", Component: GeographySection,  when: hasSubsets },
  { value: "axis",       label: "Axis",             Component: AxisSection,       key: "encodings" },
  { value: "transform",  label: "Transform",        Component: TransformSection,  key: "comparison" },
  { value: "labels",     label: "Labels",           Component: LabelsSection,     key: "labels" },
  { value: "appearance", label: "Appearance",       Component: AppearanceSection, key: "appearance" },
  { value: "typography", label: "Typography",       Component: TypographySection, key: "appearance" },
];

export function visibleSectionsFor(config, schema, { exclude } = {}) { /* ... */ }
```

Moving this out of `ChartSidebar.js` matters: that file is 1,530 lines and currently mixes section primitives, six section implementations, saved-view dialogs, and a resize handle. The split is a precondition for the rest of the work, which is why it is Phase 0.

### Sidebar height clamp

> [!important] The sidebar is clamped by CSS, not JavaScript
> The requirement is that the sidebar never exceeds the chart container's height and scrolls internally. The reliable way to get that without a `ResizeObserver` is to make the sidebar contribute **zero intrinsic height** to the grid row: the grid cell is `relative`, and the panel inside it is `absolute inset-0 overflow-y-auto`. The row is then sized entirely by the chart container, which already carries a `min-h` floor. A JS measurement approach is the fallback only if a nested `position: fixed` or transform context breaks the absolute positioning.

Below the `lg` breakpoint the layout stacks: the sidebar returns to static flow at natural height and the page scrolls normally. That is deliberate - a 400px-tall internally scrolling rail on a phone is worse than a long page.

## Sidebar Specification

Each subsection below states what the control renders, what config keys it owns, and where its options come from. These are the acceptance criteria the phase tests assert against.

### Datasets

Renders one checkbox per entry in the module's dataset list. Selection is **exclusive** - checking one unchecks the others - so it maps onto the existing `filters.source` string with no change to `chartData.js` or the API routes. The section does not render at all when a module has fewer than two datasets.

The dataset list comes from a new optional `schema.datasets` array of `{ id, label }`, falling back to `schema.sources.map(id => ({ id, label: DATASET_LABELS[id] ?? id }))`. `DATASET_LABELS` maps `DoF → "CA Department of Finance"` and `Census → "US Census"`. Today only Components of Change and Age/Sex/Race Projections carry a multi-source `sources` array, so those are the only two modules where this section appears.

> [!warning] Population & Housing's provenance filter needs a home
> Pop & Housing has `sources: null` and instead uses `provenanceFilter: true` over Source values `E-5`, `E-8`, and `Aggregated` - a genuine per-row multi-select, not a dataset toggle. Under the rule above it has one dataset, so the Datasets section hides and the provenance control is orphaned. The plan renders it as a **sub-control inside the Datasets section labeled "Data vintage"**, which forces the section to render for that module even though the dataset count is one. This is flagged in *Open Questions* because the mockup's third checkbox reads "Aggregated", which suggests the intent may be to merge provenance and dataset into a single list.

### Chart Type

A two-column grid of label-only buttons, matching the mockup, replacing today's `ChartTypeStep` card gallery with `purpose` descriptions. Order follows the mockup: Line, Bar, Choropleth Map, Forest / Whisker Plot, Diverging Bar, Symbol Map, Dot Plot, Pie / Donut, Scatter, Bubble, Matrix Heatmap, Data Table - plus Range, which is retained per decision 7 and appended after Dot Plot. Slopegraph is removed from `chartRegistry` entirely.

`schema.supportedChartTypes`, where a module declares one, still filters the grid. The section owns `config.chartType` through the existing `SET_CHART_TYPE` action and is excluded from the standalone tool's sidebar per decision 10.

### Date Range

A single- or dual-handle slider bounded by `schema.yearRange`, owning `period.year` or `period.startYear`/`period.endYear`. This is `YearRangeSection` moved unchanged except for the extraction. The section hides for modules with no temporal field, which is what `hasTemporalData()` already computes.

### Geographic Level

The mockup's most substantial change, and the section that absorbs the most existing behavior.

A `Select` chooses the level from `schema.subsets` keys and writes `filters.subset`, preserving today's side effects (forcing `source` for `subsetSource` levels, forcing Census for `States`, forcing Counties for choropleths). Beneath it, a checkbox list of **individual locations for the chosen level**, showing the first seven with a "Show more" button that reveals the rest. Changing the level clears the selection.

Selected locations are stored in a new first-class `filters.locations` array. An empty array means "no explicit selection", which preserves today's Top-N behavior. `chartData.js`'s `selectedLocations()` is extended to prefer `filters.locations` over the `selectedPlaces` layer values, keeping the layer path working for the standalone tool.

Options come from the new `view=locations` API view, consumed through `useLocationOptions(schema, filters)`, which caches per module and subset and returns a `{ status, locations, error }` envelope in the same vocabulary the preview uses.

For chart types whose categories are places - `line`, `bar`, and `divergingBar`, matching today's `CATEGORY_SELECTION_CHART_TYPES` - this same list carries a drag handle per row, writing `appearance.categoryOrder` and `appearance.hiddenCategories`. That is decision 3's "rolled into geographic level". Top-N ("Show top / bottom N values") also lives here, since on a module the ranked things are places.

### Categories (fallback)

When the chart type's categories are not places, the ordering and visibility list that would otherwise live in Geographic Level renders as its own collapsed disclosure labeled "Categories", per decision 3. It reuses the same row component as the geographic list minus the level dropdown.

### Axis

A two-column grid of role dropdowns: X-Axis, Y-Axis, Series, and Color, with Group and Tab-by-column appended. The field list per role is exactly today's `EncodingSection` logic - the chart type's `roleConstraints`, the catalog-role restriction for measures, the `group` cardinality exclusion - and `roleLabel()` continues to relabel roles for dot plots and forest plots. The `Add line` layer button that `EncodingSection` renders for line charts is removed from the module sidebar and kept in the standalone tool's Edit step.

For chart types whose required roles are not x/y (forest's `category`/`start`/`end`/`point`, the two-period charts' `start`/`end`), the section renders that chart's own roles in the same grid rather than forcing them into X/Y labels.

### Transform

Radio buttons rather than today's `Select`, matching the mockup: Actual Value, Index to Base Year (with an inline year dropdown), Numeric Change, Percentage Change. The option list is still `allowedTransforms(measure)`, so a rate measure that only permits `actual` and `percentagePointChange` renders two radios, not four. The inline year dropdown owns `period.baseYear` and is bounded by `schema.yearRange`. The section hides for chart types with `transformCapable: false`.

The benchmark-label input stays here for chart types that accept a `benchmark` role.

### Labels

Title, Subtitle, X-Axis Label, and Y-Axis Label as text inputs with the derived labels from `deriveLabels()` as placeholders, exactly as `LabelEditor` does today. The tooltip-template textarea moves to Appearance, since the mockup's Labels block has no room for it and it is a power control.

> [!note] The mockup lists "Title" twice
> The Labels block in the mockup shows two fields both labeled "Title" before Subtitle. This is almost certainly a duplication error in the mockup; the plan treats the second as **Legend Title**, which is the fifth entry in today's `LABELS` array and is otherwise unaccounted for. Confirm before building.

### Appearance

Color Palette (the existing `PalettePicker`), Legend Position, Horizontal Line Spacing (px), Vertical Line Spacing (px), and Footnote, in that order, matching the mockup.

Chart-type-conditional controls that the mockup does not show - marker mode for line, orientation for bars, center reference and the diverging-bar dashboard styling, color scale for heatmap and choropleth, the forest-plot endpoint and marker styling, the dot-plot value toggles, and the PPIC watermark switch - are appended **below** Footnote. Because each is already gated on chart type, a default line chart renders exactly the mockup's five controls; the extras only surface for the chart types that need them. The per-series color overrides that `PalettePicker` renders stay, since they were previously gated at the Advanced tier and tiers are being dropped.

### Typography

Title Size, Subtitle Size, Axis Label Size, Legend Text Size, and Decimal Places as numeric inputs in a two-column grid, extracted verbatim from today's `AppearanceSection`. Data Label Size is retained and appended, since it has no mockup slot but drives real output.

## Chart Container Specification

A single card containing a centered, brand-underlined title from `schema.label`, a bordered body, and a footer.

The body renders either the chart or the data table, driven by local `viewMode` state. Chart mode is today's `PreviewPane` with its full loading / invalid / empty / error / ready vocabulary. Data mode is `DataTableView` over the chart's displayed table, which is `displayTable(config, result)` from the already-loaded preview - no extra fetch. The three-way "Data view" radio from `ViewDataStep` (chart data / source data / entire dataset) does **not** move into the workbench; the workbench data view is always "chart data", and whole-dataset export is served by the Export Data button instead.

The footer carries a segmented "View Chart | View Data" toggle on the left and "Export Chart" and "Export Data" buttons on the right, styled as the mockup's filled brand pills. Both export buttons come from `ExportMenu`, which already renders exactly these two dropdowns internally; the work is extracting them as named exports (`ExportChartButton`, `ExportDataButton`) so the footer can place them without the wrapper's own layout. Export Data's menu keeps both its existing items - the displayed table and the entire cleaned dataset - which is what absorbs the removed "Export entire dataset" button from `ViewDataStep`.

### Phase 1 - Locations API view

**Goal.** Give the geographic multi-select a data source. Server-side only; no UI yet.

## Cross-Cutting Test Conventions

Tests live under `tests/js/` mirroring the source path, run under Vitest with `@testing-library/react`, and follow the existing pattern of `vi.hoisted()` state objects with a mocked `useChartConfig`. Three rules apply to every phase.

**Assert on behavior, not markup.** Query by role, label, and accessible name rather than class names, except where a test's whole purpose is a layout guarantee - the sidebar clamp test is the deliberate exception and should say so in a comment.

**Every async boundary gets three tests.** Loading, error, and success, matching the frontend conventions' requirement that no component renders `undefined` data. The location-options hook is the main new async boundary.

**Migration tests are not optional.** Three config-shape changes land in this work - `filters.locations` added, `tier` removed, `chartType: "slope"` retired - and each must round-trip an old saved view without throwing. A user with a bookmarked `?view=` link is the regression this catches.

## Open Questions

These need an answer before the phase that depends on them, not before the plan is accepted.

**Does the Datasets section merge dataset and provenance?** The mockup's three checkboxes read "CA Department of Finance", "US Census", and "Aggregated". The first two are dataset sources; the third is one of Pop & Housing's per-row provenance values. Either the mockup is showing two different modules' options in one illustration, or the intent is a single merged list where a module contributes whichever concept it has. The plan assumes the former and renders provenance as a labeled sub-control. *Blocks Phase 4.*

**Is the duplicated "Title" field in the Labels block intentional?** The plan treats the second as Legend Title. *Blocks Phase 8.*

**Should R/Stata code generation survive the code-editor removal?** See the warning in Phase 9. *Blocks Phase 9.*

**What happens to `?view=` deep links and embeds built against the wizard?** The plan preserves them through `ViewHydrator` and the migrations, but any external page embedding `?embed=1` should be inventoried before Phase 2 in case one depends on step state.

**Does the location multi-select need search?** Seven-plus-show-more is fine for nine regions and workable for fifty-eight counties. It is not workable for the roughly five hundred cities Pop & Housing carries. The plan does not include a search input; adding one to `GeographySection` is a small change but should be a deliberate one. *Affects Phase 6.*
