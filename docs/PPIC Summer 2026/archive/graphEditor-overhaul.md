## What the overhaul set out to do

PPIC researchers built publication charts in a fragmented workflow: analysis in
R, Stata, or Excel, then a manual rebuild in Datawrapper. The V3 site already had
a working chart editor, but it charted only the five migrated modules, offered no
color control, no image or data export, and no way to bring your own table. The
overhaul aimed to turn it into a general-purpose graph editor that could replace
the R/Stata/Excel → Datawrapper hop.

Five pillars, as originally stated:

1. **Bring your own data** - paste or upload a table, correct it in place, chart it.
2. **Two synchronized editing modes** - a GUI sidebar and a code editor over the same declarative config.
3. **Take your work with you** - image, data, and config export, plus generated R/Stata code.
4. **More chart forms, fewer components** - chart families configured as variants of base types.
5. **Three settings tiers** - Basic, Moderate, Advanced, so a first-time user saw five controls and a power user saw all of them.

## What still holds

The overhaul's central architectural decision survived intact and is still the
thing the whole feature rests on: **the declarative chart config is the single
source of truth**. A chart is plain JSON; `toPlotly` turns config plus fetched
data into a figure; saved views, deep links, and iframe embeds all serialize that
same object and never a rendered figure or a data snapshot.

So did spec v2 (`chartSpec.js`), the client-safe `lib/visualization/` seam, the
module-schema plug-in system, the validation guardrails, the palette single-owner
build step, and bring-your-own-data.

## What was withdrawn on 2026-07-28

| Pillar | Outcome |
|---|---|
| **Code editor** (pillar 2) | Withdrawn. The parsers recognised only the subset the generator emitted, so anything hand-written surfaced as `CODE_UNSUPPORTED` warnings. The R/Stata **generators** were kept, dormant, against a future "copy the code for this chart" export item. |
| **Settings tiers** (pillar 5) | Withdrawn. The tiers hid controls the sections already gate by chart type and schema, so in practice they meant a user could not find a control they had been told about. |
| **Slopegraph** | Withdrawn as a chart type. Both it and the Range chart were two-period views of one measure; a line renders the same bindings. Stored views carrying `chartType: "slope"` normalize to `line` with a `CHART_TYPE_RETIRED` warning. |
| **One editor for both surfaces** | Withdrawn. `ModuleEditor` and the standalone tool were the same `VisualizationWizard` with a different `steps` prop. |

## The divergence this document predates

The overhaul assumed one editor served both readers. It did not. A researcher
opening `/pophousing` wants to explore a curated dataset; a researcher opening
`/visualization-tool` wants to chart a spreadsheet. The step wizard suited the
second and got in the way of the first, who had no data to import and no reason
to page through four steps to change a color.

So the surfaces split:

- **`/[module]`** renders `ModuleWorkbench` - a **single-screen** workbench with a persistent control sidebar beside a chart container, no step navigation.
- **`/visualization-tool`** keeps the step **wizard** (Import → Chart Type → Edit → Export), along with presets, saved views, the multi-chart workspace, trace layers, and the activity log.

Both compose their controls from one shared section registry, so the split is a
difference of shell and composition, not of capability duplicated twice.
