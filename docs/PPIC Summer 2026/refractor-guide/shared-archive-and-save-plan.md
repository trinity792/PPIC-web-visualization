# Shared `archive_and_save`

> [!info] Who this is for and how to read it
> This guide has two halves. **The first half needs no programming background**: it explains what the shared archive mechanism does, why six copies of it existed, and what changed for the data. **The second half is a programmer reference**, function by function, with the legacy lineage of each - which module-local implementation it replaced and what changed in the replacement.
>
> Unlike the module guides beside it, this one describes a *shared mechanism* rather than a module migration, so "legacy" here means the six module-local implementations that existed before the hoist, not the original Jupyter notebooks.

> [!success] Built, live-verified, and migrated
> All six modules ran live on 2026-08-07, the archive path was exercised in production by `building_permits` and `rhna_progress`, and the nine pre-existing archive files were renamed to the new format with every SHA-256 digest re-verified afterward. 1316 unit tests pass. ## What this does

Every module in the project ends its pipeline the same way: it has just computed a fresh dataset, and there is already a file on disk holding the previous version. Three things have to happen, in an order that matters. The old version gets preserved into an archive folder so it can be recovered. The new version replaces it. And if the new data turns out to be identical to the old, nothing should happen at all, because rewriting an unchanged file makes every run look like a change when someone later reviews the history.

That is `archive_and_save`. One function, in `scripts/shared/archives/dataset_archive.py`, used by all six modules that write a dataset.

### Why there were six of them

The mechanism is not specific to any module. It takes a table, a file path, and an archive folder, and decides whether to write. Nothing about population projections makes that decision differently from building permits. But it was written six separate times, once per module, and the six copies drifted apart in ways nobody intended:

- **Three different filename schemes.** Two modules produced `BuildingPermits_08-04-26.csv`, two produced `DemographicProjections_Current_08-04-26.csv`, and two produced no date at all, just `ComponentsOfChange_Current.csv` with a `_1`, `_2` counter tacked on when the name was taken.
- **Two ways of deciding whether the data changed.** Four modules compared the old and new files; two never compared at all and simply rewrote every time.
- **Two incompatible ideas about the old file.** Four modules *copied* it into the archive. Two *moved* it.

That last difference was the serious one, and it is covered below.

### The filename, and why it changed

Archive files are moving onto external storage, where a person browses them instead of a script reading them. Two things start to matter that did not matter while the archive sat in a folder on one machine. A file should say what it is once it has been moved out of its folder. And a directory listing should sort into chronological order on its own.

The old format did neither. `01-15-26` sorts before `02-03-25`, because month-first ordering is not chronological ordering, and a file named `ComponentsOfChange_Current_2.csv` says nothing about when it was made. The new format is:

```text
{module_id}_{prefix}_{YYYY-MM-DD}.csv
```

| Module | Before | After |
|---|---|---|
| `building_permits` | `BuildingPermits_08-04-26.csv` | `building-permits_BuildingPermits_2026-08-04.csv` |
| `projections` | `DemographicProjections_Current_08-04-26.csv` | `projections_DemographicProjections_2026-08-04.csv` |
| `rhna_progress` | `RHNAProgress_08-04-26.csv` | `rhna-progress_RHNAProgress_2026-08-04.csv` |
| `housing_stress` | `HousingStress_Current_08-04-26.csv` | `housing-stress_HousingStress_2026-08-04.csv` |
| `housing_stress` backfill | `HousingStress_Historical_07-13-26.csv` | `housing-stress-backfill_HousingStress_2026-08-04.csv` |
| `components_of_change` | `ComponentsOfChange_Current.csv` (undated) | `components-of-change_ComponentsOfChange_2026-08-04.csv` |
| `pophousing` | `PopHousing_Current.csv` (undated) | `pophousing_PopHousing_2026-08-04.csv` |

Year-month-day sorts correctly as plain text, so a listing is chronological with no tool and no sorting option. The module name at the front means a file dropped into a shared folder still identifies itself.

### The data-loss window this closed

This is the part that mattered most, and it had nothing to do with filenames.

Two modules, `components_of_change` and `pophousing`, archived the old file by **moving** it. For a brief moment during every run, the canonical dataset did not exist anywhere except inside a hidden archive folder, under a name a reader would not think to look for. If the program crashed in that window, or the machine lost power, or a validation check failed partway through writing the replacement, the module was left with no dataset at its expected location.

The shared helper copies instead. The old file stays exactly where it is until the new one is completely written and verified, and then the two are swapped in a single operation the operating system guarantees cannot be interrupted halfway. **At every instant of a run, a valid dataset exists at the expected path.** This is the one property in the design that nothing else may be traded against.

### Doing nothing when nothing changed

The same two modules had a second gap: they never checked whether the new data differed from the old. Every run archived and rewrote, whether or not anything had changed.

The archive itself shows this happening. `data/archive/components-of-change/` holds two files written 78 seconds apart on July 1, 2026, and they are **byte-for-byte identical**. The pipeline ran twice, produced exactly the same output both times, and archived and rewrote the dataset anyway. Under the shared helper the second run would have done nothing at all.

The comparison is done by reading the existing file in small pieces and computing a compact fingerprint, rather than loading the whole thing into memory. On the projections dataset, which is roughly 87MB, this is the difference between about 189MB of peak memory and about 2MB. That optimization was originally written for the projections module alone; hoisting it into the shared helper handed the same improvement to the other five as a side effect.

## Programmer reference

### `scripts/shared/archives/dataset_archive.py`

The shared mechanism. Imports `hashlib`, `shutil`, `datetime.date`, and `pathlib`. No pandas import: it accepts a dataframe but only ever calls `.to_csv()` on it.

#### `build_archive_filename(module_id, current_path, today, time_of_day=None)`

Builds `{module_id}_{prefix}_{YYYY-MM-DD}.csv`, where `prefix` is `current_path.stem.split("_")[0]`.

Separate from `archive_and_save` rather than inlined as an f-string for two reasons: the legacy rename script calls it, so a second implementation of the format cannot drift from the first, and a future change to the format is one edit in one place.

`time_of_day` is optional and defaults to `None`, which produces the plain dated name. When supplied, the name gains a `T{HHMMSS}` suffix. **`archive_and_save` never passes it.** Day granularity for live writes is a deliberate, test-pinned decision, covered under [Flagged Issues](#flagged-issues-and-fragilities). The parameter exists for the rename script, which has to separate archives written minutes apart.

*Legacy lineage:* the `prefix` rule is exactly what `building_permits` and `rhna_progress` did (`current_path.stem.split("_")[0]`, which drops the `_Current` suffix). `projections` and `housing_stress` used the full stem, so `_Current` survived into their archive names; adopting the shorter rule is what made the `module_id` prefix necessary, since without it the two `housing_stress` writers would collide.

#### `archive_and_save(dataframe, current_path, archive_directory, module_id, already_compared=False)`

The public entry point. Returns the output path when a write happened and `None` when the data was unchanged, which is the contract every caller depends on: orchestrators assign the result and check it for `None` to decide whether to log a write. A helper that returned a path unconditionally would make every run look like a change in `logs/pipeline-runs.jsonl`.

The order of operations is load-bearing:

1. Serialize the frame to CSV bytes.
2. If a canonical file exists and `already_compared` is false, stream a SHA-256 of it and compare against the hash of the new bytes. On a match, return `None` immediately, having touched nothing - the existing file keeps its contents *and its modification time*.
3. Otherwise `shutil.copy2` the existing file into the archive under the built filename.
4. Write the new bytes to a sibling `.tmp` file, then `Path.replace()` it over the canonical path. `replace` is atomic on a single filesystem.
5. In a `finally`, remove the `.tmp` if it still exists, so a failed write leaves no fragment.

`already_compared=True` skips step 2 and always archives and writes. Only `rhna_progress` passes it, because its caller has already established the data is new one level up.

*Legacy lineage:* replaces six implementations. The streamed-hash comparison and `shutil.copy2` come from `projections` and `housing_stress`, which had it already. The atomic `.tmp` plus `replace` pattern was present in four of the six. The `prefix` rule comes from `building_permits`. What is genuinely new is that `components_of_change` and `pophousing` now copy rather than move, and now compare at all.

#### `_sha256_of_file(path)`

Reads in 1 MiB chunks and returns the hex digest. Private. The chunking is the entire point: it never holds a second full copy of an 87MB file in memory.

*Legacy lineage:* identical private helpers existed in both `projections` and `housing_stress`; both were deleted.

### `scripts/shared/archives/rename_legacy_archives.py`

A one-off migration, not part of any pipeline. Renames pre-existing archive files to the new format so a directory does not hold two conventions and sort correctly under neither. Imports `re`, `collections.defaultdict`, `dataclasses`, `datetime`, and `pathlib`, plus `build_archive_filename` from the module above.

> [!danger] File contents are never touched
> The script uses `Path.rename()` only, never a copy-then-delete. A bug in it costs a name, not data. It also validates the entire plan before renaming anything, so a plan that cannot be satisfied changes nothing at all.

#### `_module_id_for(directory_name, file_name)`

Resolves which module owns one archived file. Reads from `_DIRECTORY_MODULE_IDS`, a hand-written literal dict, because **three of six archive directories do not match their module id**: `demographic-projections` maps to `projections`, `RHNA-progress-report` to `rhna-progress`, and `housing-population` to `pophousing`. Deriving the id from the directory name would be wrong in half the cases.

`housing-stress` is deliberately absent from that dict and resolved per file, because it is the one directory holding two writers' archives. `HousingStress_Historical_*` maps to `housing-stress-backfill`, `HousingStress_Current_*` to `housing-stress`. Raises rather than guessing on anything else.

#### `_local_mtime(path)` and `_resolve_date(path)`

`_resolve_date` returns a `(date, inferred_from_mtime)` pair. A date parsed out of an `mm-dd-yy` filename returns `False`; a date read from the file's modification time returns `True`, and the caller prints that distinction, because an inferred date is weaker evidence than a parsed one. A two-digit year that resolves before 2020 raises rather than being guessed at.

`_local_mtime` reads the modification time on the **local** clock, matching `date.today()` in `dataset_archive.py`. Reading it in UTC shifts anything modified after roughly 5pm Pacific onto the following day, which would have dated two of the real pophousing archives a day late.

> [!note] On these files, mtime means "data vintage", not "archive date"
> `shutil.copy2` and `shutil.move` both preserve the source file's modification time, so an archive's mtime records when that dataset version was written to the canonical path, not when it was archived. This is why `HousingStress_Current_07-14-26.csv` carries an mtime of July 1 while its name says July 14: both are correct, thirteen days apart. It also means the mtime fallback yields the more meaningful of the two dates, which is what makes it sound rather than a guess. Full evidence in [[pre-archive-save-refractor]].

#### `_archive_directories(archive_root)`

Yields every subdirectory holding at least one CSV, **including unmapped ones**, so `_module_id_for` raises on a directory nobody added to the map rather than the script silently skipping it. Directories with no CSVs are skipped without comment, because an empty `RHNA-progress-report/` is a normal state.

#### `_disambiguate_same_day_collisions(plan)`

Groups the planned renames by destination and re-plans any group with more than one member, rebuilding each with its local mtime time-of-day so the names become `..._2026-07-01T155638.csv`. Files that do not collide keep the plain readable date.

This exists because day granularity collapses the two identical `components_of_change` archives written 78 seconds apart, and without it the collision check refused the entire nine-file run. Anything this pass cannot separate - the same date *and* the same whole second - falls through to `_validate_plan` and stops the run, which is the case where a person has to look.

#### `_validate_plan(plan)`

The backstop. Raises `ValueError` if two sources still map to one destination, naming both, and `FileExistsError` if a destination is already occupied. Runs before any rename, so a bad plan leaves the directory untouched.

#### `rename_legacy_archives(archive_root, dry_run=True)`

The entry point. **Defaults to dry-run**, so an accidental call is inert. Prints the mapping either way, flagging any date or time inferred from mtime. The CLI wraps it with `--archive-root` and `--execute`.

`_NEW_FORMAT_PATTERN` makes a second run a no-op by skipping already-migrated names. Its optional `(T\d{6})?` group is the single most consequential line in the file: without it a disambiguated file reads as legacy on the next run and gets renamed again into nonsense, and that failure is invisible until the second run.

### Call sites

Seven, across six modules. `module_id` is passed explicitly rather than derived, because three archive directories do not match their module id and because it makes the archive filename and the `logs/pipeline-runs.jsonl` run record provably the same string.

| Caller | `module_id` | Canonical path argument |

Four modules re-export `archive_and_save` from their `output/finalize_dataset.py` with a `# noqa: F401` comment, so their orchestrators' existing import lines keep working. `rhna_progress` and `pophousing` import the shared helper directly.

> [!danger] The two `housing_stress` writers stay apart only because of `module_id`
> `prefix` is `stem.split("_")[0]`, which yields `HousingStress` for **both** `HousingStress_Current.csv` and `HousingStress_Historical.csv`. With a single `module_id`, the live pipeline and the backfill would write the same filename, and the deep-history seed archive would be silently overwritten by the live archive on any day both ran. The backfill passing `module_id="housing-stress-backfill"` is the only thing preventing it, and `test_backfill_passes_distinct_module_id_for_seed_archive` is the only test that would catch its absence.

## From initial refactor to current state

The first implementation delivered the shared helper and all six migrations, passing 1306 tests. A subsequent audit found nine issues, all since resolved.

| Issue | Resolution |
|---|---|
| The legacy rename had never been run, and hard-failed on the real archive over the two identical July 1 Components files | `_disambiguate_same_day_collisions` added; the nine-file dry run now matches its expected mapping exactly |
| `_resolve_date` reported every date as inferred from mtime, including parsed ones | Returns `False` on the parsed branch; a test now asserts the *absence* of the mtime note for a dated file |
| mtime was read in UTC while the helper dated in local time, misdating two real archives by a day | `_local_mtime` reads the local clock; a fixture at 18:00 local pins it |
| An archive directory with no module id mapping was silently skipped | `_archive_directories` yields unmapped directories so `_module_id_for` raises |
| `pophousing_pipeline.py` kept `write_housing_output` and `archive_or_delete_files` imported purely as test monkeypatch seams, asserting nothing | Both imports and both patches deleted; `test_pipeline_does_not_import_the_retired_write_seams` guards the removal |
| The frozen-clock fixture used `raising=False`, so it could stop freezing silently, and patched a `datetime` attribute the module does not have | `raising=True`, dead class and patch removed, stale red-phase docstrings rewritten |
| `shared-archive-and-save-refractor.md` still read as an unbuilt proposal | Set to `Status: Archive` with a superseded callout pointing here |
| **Found by the first live run:** `pophousing`'s summary hardcoded `output_path` to the canonical path, so an idempotent run recorded a write that never happened | The summary now reports `archive_and_save`'s return value verbatim, matching its five siblings; the unit test that had pinned the wrong behavior was corrected |

The audit also confirmed three things were correct as built and should not be changed: the copy-not-move invariant is genuinely tested at the moment it matters (by hooking `Path.replace` and inspecting the canonical file mid-operation), the `module_id` collision fix is real, and the day-granularity same-day overwrite is deliberate rather than overlooked.

## Flagged issues and fragilities

> [!warning] Two refreshes of one module on the same day still overwrite each other
> `{YYYY-MM-DD}` has the same resolution the old `{mm-dd-yy}` did. The second run's archive replaces the first's. This is accepted rather than overlooked: the name stays readable, and manual roughly-monthly refreshes do not hit it. `test_a_second_run_on_the_same_day_overwrites_the_existing_archive_entry` pins the behavior so a future change is a deliberate edit. The fix, if a schedule is ever added, is to pass `time_of_day` from `archive_and_save` - the escape hatch is already built and already tested, it is simply not wired.

> [!warning] A failed write leaves an orphan archive entry
> If the atomic replace raises, the archive copy made just before it survives. The canonical file is intact and unchanged, so nothing is lost, but the archive gains an entry for a version that is still current. Harmless, and preferable to the alternative of deleting an archive during error handling.

> [!note] Green tests are not a working pipeline, demonstrated again
> This is the project's most repeated lesson: every module's orchestrator tests mocked the file seams and passed while the real run crashed. It held here too. All 1316 unit tests passed, and the first live run on 2026-08-07 still surfaced the `pophousing` run-record defect above, because the test suite had pinned the wrong expectation rather than the correct contract. Nothing in a mocked suite would ever have caught it.

> [!note] Nothing downstream parses archive filenames
> Checked specifically. The `filename_pattern` regexes in `pophousing/archives/e5_retention.py` and `projections/acquisition/dof_p3_downloader.py` match *source downloads*, not archived datasets. A repository-wide search found the counter-suffix pattern only in `test_file_retention.py`. `data/archive/` is gitignored, so a personal script outside the repository could depend on these names invisibly; the user has confirmed none is known.
